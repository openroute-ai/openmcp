# OpenMCP 聚合 MCP / A2A / Skills 收费模式 — 合规要点清单

> **文档性质**：产品与合规落地清单，供内部对齐与法务评审，**不构成法律意见**。  
> **适用范围**：以网站 + OpenWork / OpenMCP Studio 客户端获客与分发，聚合 Provider 的 MCP / A2A / Skills，向终端用户收费并向 Provider 结算。  
> **建议主体假设**：中国大陆运营与收款（若主体/收款地不同，支付与资质条款需重做定性）。  
> **更新日期**：2026-10-11

---

## 1. 结论（先读）

| 问题 | 判断 |
|------|------|
| 模式是否可行？ | **可行**，前提是做成合规的**资产交易 / 分发平台**（撮合 + 平台服务），而非无授权转售第三方资产。 |
| 网站 / OpenWork 客户端获客？ | **可以**；入口形态本身不是主要障碍，风险在授权链、资金流、内容安全与经营资质。 |
| 推荐商业结构 | Provider 上架其有权分发的资产；平台提供发现、评测、安装、计费、结算；用户购买「资产使用权 + 平台交付 / 网关等增值服务」；平台收服务费或抽成。 |

---

## 2. 推荐与应避开的商业结构

### 2.1 推荐（低摩擦、好辩护）

1. **平台撮合**：Provider 是商品权利人；平台是展示、交易、交付与结算通道。
2. **自营增值服务单独计价**：统一网关（对外不暴露底层品牌）、推荐、企业控制面、钱包、技术支持等 —— 收费依据最清晰。
3. **清晰的许可层级**：个人 / 团队 / 企业；禁止用户再分发或二次上架（除非协议明示）。
4. **免费与付费并存**：免费获取仍走登录、鉴权、安全扫描与审计，避免「免费用 = 无责任」。

### 2.2 高风险、应避免

1. 未获授权爬取、镜像、改名后向用户收费。
2. 将第三方 Skill / MCP 包装成「平台自有商品」卖断。
3. 对调用结果、生成内容或业务合规做无限担保。
4. 资金实质沉淀、拆分打款却未按支付 / 结算合规定性（所谓「二清」风险）。
5. 对外宣传「官方认证 / 绝对安全 / 无法律风险」等夸大表述。

## 3. 合规要点清单（按优先级）

### P0 — 上线收费前必须闭环

#### 3.1 授权与知识产权

- [ ] **Provider 上架协议**：保证对 MCP / A2A / Skills 有商用分发权；授权平台代为展示、分发、代收代付或抽成结算。
- [ ] **用户许可协议（EULA / ToS）**：许可范围、禁止再分发、退款规则、账号共用限制。
- [ ] **开源许可证门禁**：GPL 等强传染性协议、商标与品牌冒用、第三方 SDK 条款冲突 —— 扫描或人工审核后才可「付费上架」。
- [ ] **来源追溯**：资产版本、作者、仓库 / 包哈希、变更记录可审计。

#### 3.2 资金流与支付结算

- [ ] 明确资金流图：用户 → 谁收款 → 是否过平台账户 → Provider 结算周期与抽成。
- [ ] 由法务 / 支付顾问按**实际资金流**定性：平台服务费结算 vs 支付业务 / 二清。
- [ ] 支付通道（微信 / 支付宝等）商户主体与网站经营主体一致或有合法委托关系。
- [ ] 退款、发票、对账、异议处理流程与客服话术。
- [ ] Provider 结算协议：税率、发票、冻结与违规扣款条款。

#### 3.3 可执行内容安全（Skills / MCP 等同软件分发）

- [ ] 上架前安全扫描（至少：恶意脚本、敏感权限、外连黑名单、供应链基础检查）。
- [ ] 安全等级 / 发布门禁与「人工 certified」区分（硬门禁 ≠ 营销徽章）。
- [ ] 恶意或违规资产的下架、用户通知、已购用户处理策略。
- [ ] 操作与安装日志留存，满足追溯与配合监管查询的需要。

#### 3.4 用户协议、隐私与数据

- [ ] 隐私政策覆盖：注册登录、Device Code、安装回调、账单、用量、日志。
- [ ] 最小必要收集；目的变更需再同意。
- [ ] 若模型或网关涉及跨境传输：跨境评估 / 标准合同等路径提前设计（按实际部署地）。
- [ ] 账号注销与个人数据删除 / 导出路径。

### P1 — 面向中国大陆公开运营时尽快补齐

#### 3.5 经营与展示资质

- [ ] 网站 ICP 备案等基础资质（按主体与接入方式落实）。
- [ ] 若业务被认定为特定互联网信息服务，评估是否还需额外许可（以律师意见为准）。
- [ ] 客户端分发：安装权限说明、自动更新、企业内网 / 私有化部署承诺可兑现。

#### 3.6 Provider 与 KYC

- [ ] 个人 / 企业 Provider 分类准入（与现有产品：Skills 偏个人、MCP/A2A 偏企业等规则对齐）。
- [ ] 必要的实名 / 企业认证与结算账户核验。
- [ ] 历史违规、反复上下架策略。

#### 3.7 宣传与产品文案红线

- [ ] 安全评级、评测分仅作参考，不暗示「监管认证」。
- [ ] 不承诺代用户完成违法用途；滥用监测与停权条款写进 ToS。
- [ ] OpenWork / Studio 与 OpenMCP 品牌边界清晰；隐藏底层网关实现品牌（产品策略），同时不虚假陈述基础设施归属。

### P2 — 增强项（规模化后再做深）

- [ ] 青少年 / 高风险行业使用限制策略（如需）。
- [ ] 出口管制与制裁名单筛查（若有跨境企业客户）。
- [ ] 保险、重大事故响应与对外披露预案。
- [ ] 定期第三方安全审计与渗透测试。

## 4. 与获客形态的关系（网站 + OpenWork 客户端）

| 形态 | 合规关注点 |
|------|------------|
| 网站商城 / 详情 / 购买 | 展示真实价格与许可；支付与退款入口可达；资质与协议链接可见。 |
| Store MCP / Device Code 安装 | 安装鉴权与 entitlement 一致；不可绕过付费墙下载正式包。 |
| OpenWork / Studio 客户端 | 权限与数据说明；更新通道安全；企业版数据驻留承诺与实现一致。 |
| 统一网关（对用户隐藏实现细节） | 产品可隐藏第三方品牌；合同与隐私政策仍须如实描述数据处理与责任边界。 |

---

## 5. 建议落地顺序

1. **合同包**：Provider 协议 + 用户 ToS / EULA + 隐私政策（中文主文）。
2. **资金流法务定性**（决定能否「平台代收再结算」及如何落地）。
3. **安全扫描 + 下架 playbook** 写入产品与运营手册。
4. **支付与发票** 打通后再放开大规模付费投放。
5. **对外获客**（网站 SEO、客户端分发、渠道合作）在 1–4 有初版后再放量。

## 6. 协议条款清单（起草时至少覆盖）

### Provider 侧

- 权利保证与侵权赔偿  
- 上架内容合规承诺（含可执行代码安全）  
- 授权范围（展示、分发、测评、缓存、全球或区域）  
- 定价权、抽成、结算周期、税票  
- 下架、处罚、数据与评价权属  

### 用户侧

- 账户与实名（如需）  
- 许可类型与禁止行为  
- 付费、续费、退款  
- 风险提示（第三方资产、AI 输出）  
- 违规停权与争议解决（管辖）  

---

## 7. 对外宣传话术红线（摘要）

| 避免 | 可改为 |
|------|--------|
| 「官方认证 / 政府认可」 | 「平台安全扫描通过 / 人工复核（如有）」 |
| 「绝对安全、无法律风险」 | 「持续扫描与分级，不替代用户自身合规」 |
| 「转卖正版 MCP」 | 「Provider 授权上架，平台提供交易与交付」 |
| 「资金由平台随便代收」 | 按法务定性后的标准表述（结算 / 指定支付机构等） |
