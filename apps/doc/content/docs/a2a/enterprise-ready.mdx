---
title: '企业级特性'
---

Agent2Agent（A2A）协议的核心理念是以企业需求为设计宗旨。A2A 并非为安全和运维发明新的专有标准，而是力求与现有企业基础设施和广泛采用的最佳实践无缝集成。这种方法使组织能够利用其在安全、监控、治理和身份管理方面的现有投入和专业能力。

A2A 的一个关键原则是智能体通常是**不透明的**（opaque），因为它们不会彼此共享内部记忆、工具或直接资源访问。这种不透明性自然与标准的客户端-服务端安全范式保持一致，将远程智能体视为标准的基于 HTTP 的企业应用。

## 传输层安全（TLS）

确保传输中数据的机密性和完整性，对任何企业应用来说都是基础要求。

- **强制 HTTPS**：生产环境中的所有 A2A 通信都必须通过 `HTTPS` 进行。
- **现代 TLS 标准**：实现应使用现代 TLS 版本。建议使用 TLS 1.2 或更高版本。应使用强健的、行业标准的密码套件，以保护数据免遭窃听和篡改。
- **服务器身份验证**：A2A 客户端应在 TLS 握手期间，通过对照受信任证书颁发机构验证 A2A 服务器的 TLS 证书，来确认服务器身份。这可以防止中间人攻击。

## 认证

A2A 将认证委托给标准 Web 机制。它主要依赖 HTTP 头部以及 OAuth2 和 OpenID Connect 等成熟标准。认证要求由 A2A 服务器在其 Agent Card 中公布。

- **载荷中无身份信息**：A2A 协议载荷（例如 `JSON-RPC` 消息）不直接携带用户或客户端身份信息。身份在传输/HTTP 层建立。
- **Agent Card 声明**：A2A 服务器的 Agent Card 在其 `security` 字段中描述其支持的认证方案，并与 OpenAPI 规范中定义的认证方案保持一致。
- **带外凭据获取**：A2A 客户端通过 A2A 协议本身之外的过程获取必要凭据，例如 OAuth 2.0 令牌或 API 密钥。示例包括 OAuth 流程或安全密钥分发。
- **HTTP 头部传输**：凭据**必须**按照所选认证方案的要求，通过标准 HTTP 头部传输。示例包括 `Authorization: Bearer <TOKEN>` 或 `API-Key: <KEY_VALUE>`。
- **服务端校验**：A2A 服务器**必须**使用 HTTP 头部中提供的凭据对每个传入请求进行认证。
    - 如果认证失败或凭据缺失，服务器**应该**以标准 HTTP 状态码响应：
        - `401 Unauthorized`：如果凭据缺失或无效。此响应**应该**包含 `WWW-Authenticate` 头部，以告知客户端支持的认证方法。
        - `403 Forbidden`：如果凭据有效，但经过认证的客户端无权执行所请求的操作。
- **任务内认证（次要凭据）**：如果某个智能体在任务期间需要额外的凭据来访问不同的系统或服务（例如，代表用户使用某个特定工具），A2A 服务器会向客户端表明需要更多信息。客户端随后负责通过 A2A 协议本身之外的过程（例如 OAuth 流程）获取这些次要凭据，并将其提供给 A2A 服务器以继续任务。

## 授权

客户端通过认证后，A2A 服务器负责对请求进行授权。授权逻辑取决于智能体的实现、其处理的数据以及适用的企业策略。

- **细粒度控制**：授权**应该**基于经过认证的身份实施，该身份可以代表最终用户、客户端应用或两者。
- **基于技能的授权**：访问可以按技能进行控制，如 Agent Card 中公布的那样。例如，特定的 OAuth 作用域**应该**授予经过认证的客户端调用某些技能的权限，而非其他技能。
- **数据和操作级授权**：与后端系统、数据库或工具交互的智能体，在通过这些底层资源执行敏感操作或访问敏感数据之前，**必须**实施适当的授权。智能体充当守门人。
- **最小权限原则**：智能体**必须**仅授予客户端或用户通过 A2A 接口执行预期操作所需的必要权限。

## 数据隐私与机密性

保护智能体之间交换的敏感数据至关重要，需要严格遵守隐私法规和最佳实践。

- **敏感性认知**：实现者必须敏锐地意识到 A2A 交互中 Message 和 Artifact 部分所交换数据的敏感性。
- **合规性**：根据所涉及的领域和数据，确保符合相关数据隐私法规，例如 GDPR、CCPA 和 HIPAA。
- **数据最小化**：避免在 A2A 交换中包含或请求不必要的敏感信息。
- **安全处理**：根据企业数据安全策略和监管要求，保护传输中的数据（按强制要求使用 TLS），以及智能体持久化的静态数据。

## 追踪、可观测性与监控

A2A 对 HTTP 的依赖，使其能够轻松集成标准的企业追踪、日志记录和监控工具，为智能体间工作流提供关键的可见性。

- **分布式追踪**：A2A 客户端和服务器**应该**参与分布式追踪系统。例如，使用 OpenTelemetry 通过标准 HTTP 头部（例如 W3C Trace Context 头部）传播追踪上下文，包括 trace ID 和 span ID。这为调试和性能分析提供端到端的可见性。
- **全面的日志记录**：在客户端和服务器端记录详细信息，包括 taskId、sessionId、相关 ID 和追踪上下文，以进行故障排查和审计。
- **指标**：A2A 服务器应公开关键运行指标，例如请求速率、错误率、任务处理延迟和资源利用率，以支持性能监控、告警和容量规划。
- **审计**：审计重要事件，例如任务创建、关键状态变更和智能体操作，尤其是在涉及敏感数据或高影响操作时。

## API 管理与治理

对于对外暴露、跨越组织边界、甚至在大企业内部使用的 A2A 服务器，强烈建议与 API 管理解决方案集成，因为这样可以提供：

- **集中式策略执行**：一致地应用安全策略，例如认证与授权、限流和配额。
- **流量管理**：负载均衡、路由和中介。
- **分析与报告**：深入了解智能体的使用情况、性能和趋势。
- **开发者门户**：促进对启用 A2A 的智能体的发现，提供 Agent Card 等文档，并简化客户端开发者的接入流程。

通过遵循这些企业级实践，A2A 实现可以在复杂的组织环境中安全、可靠且可管理地部署。这有助于建立信任，并实现可扩展的智能体间协作。
