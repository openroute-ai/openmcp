---
title: '扩展与绑定治理'
---

A2A 组织对[扩展](/docs/a2a/extensions)和[自定义协议绑定](/docs/a2a/custom-protocol-bindings)使用统一的治理框架。本文档定义了在 A2A 组织内提出、开发、推广和维护这些产物的正式流程。

任何人都可以独立开发和发布扩展或自定义协议绑定。此处描述的层级和生命周期专门适用于托管在 `a2aproject` GitHub 组织下的产物。

## 层级

扩展和自定义协议绑定在 `a2aproject` 组织内都采用两层体系。仓库命名和 URI 前缀因类型而异：

|                          | 扩展                                | 自定义协议绑定                             |
| :----------------------- | :---------------------------------------------- | :--------------------------------------------- |
| 官方仓库前缀             | `ext-{name}`                                    | `cpb-{name}`                                   |
| 实验性仓库前缀           | `experimental-ext-{name}`                       | `experimental-cpb-{name}`                      |
| 官方 URI 前缀            | `https://a2a-protocol.org/extensions/`          | `https://a2a-protocol.org/bindings/`           |

### URI 命名空间

官方 URI 前缀是规范性的命名空间标识符，用于为扩展和自定义协议绑定分配全局唯一的 URI。智能体和客户端在 Agent Card、头部和协议消息中引用这些 URI，以声明和协商支持。

前缀下的各个 URI 标识特定的产物，并在适用时标识其版本——例如 `https://a2a-protocol.org/extensions/{name}/v1` 或 `https://a2a-protocol.org/bindings/{name}/v1`。

这些 URI 是标识符，不期望 HTTP 访问。

### 官方

官方产物在 `a2aproject` GitHub 组织下开发和维护，并由 TSC 官方推荐。每个仓库都有 `MAINTAINERS.md` 中指定的维护者。

**要求：**

- 规范必须使用与核心规范相同的语言（[RFC 2119](https://tools.ietf.org/html/rfc2119)）
- 必须依据 Apache 2.0 许可
- 必须至少有一个参考实现
- 应该在 A2A 网站上提供相关文档

### 实验性

实验性产物为社区贡献者提供了一条孵化路径，让他们在毕业并晋升为官方状态之前，先对想法进行原型开发和协作。

**创建要求：**

- 实验性仓库只有在获得 A2A 维护者赞助的情况下才能创建
- 赞助维护者负责对实验性产物进行初始监督
- 实验性仓库必须在 README 中明确标示其实验性/非官方状态
- 任何已发布的包必须使用能明确标示实验性状态的命名
- TSC 保留监督权，包括归档或移除实验性仓库的能力

## 生命周期

扩展和自定义协议绑定依次经历以下阶段。

### 提案阶段

任何社区成员都可以提出扩展或自定义协议绑定：

1. **发起 Issue**：在 `a2aproject/A2A` 主仓库中创建一个 issue，描述：
    - 摘要，说明扩展的用途或绑定的传输方式及用例
    - 动机，解释为何无法通过核心协议或现有标准绑定实现
    - 初步的技术方案或规范草稿
2. **社区讨论**：提案向社区开放，收集反馈并进行完善

### 维护者赞助

提案要进入实验性状态，需要：

1. **获得赞助**：A2A 维护者必须同意赞助该提案
2. **创建仓库**：赞助维护者在 `a2aproject` 下创建 `experimental-ext-*` 或 `experimental-cpb-*` 仓库
3. **监督**：赞助维护者提供初始监督，并确保与 A2A 设计原则保持一致

### 实验性开发

处于实验性状态期间：

- 贡献者迭代规范及参考实现
- 早期采用者可以使用实验性产物，但需理解可能会发生破坏性变更
- 收集并吸纳社区反馈
- 实验性仓库必须明确标示其非官方状态

### 毕业晋升为官方状态

要将实验性扩展或绑定晋升为官方状态：

1. **成熟度要求**：
    - 至少有一个生产质量的参考实现
    - 符合 A2A 标准的文档
    - 有社区采用或感兴趣的证据
    - 维护者明确承诺进行持续维护
2. **晋升提案**：在 `a2aproject/A2A` 中发起 issue，内容包括：
    - 引用实验性仓库及其实现
    - 总结社区反馈和采用情况
    - 为官方产物建议的维护者
3. **TSC 投票**：
    - 该提案被加入 TSC 会议议程
    - **法定人数要求**：TSC 有投票权的成员中至少有 50% 必须出席
    - **批准**：需要出席成员多数投票通过（依据 A2A 治理规定）
    - TSC 可在最终投票前要求修订
4. **验收**：
    - （扩展）仓库从 `experimental-ext-*` 更名为 `ext-*`；文档添加到 A2A 网站的扩展页面
    - （自定义协议绑定）仓库从 `experimental-cpb-*` 更名为 `cpb-*`；文档添加到 A2A 网站的自定义协议绑定页面

### 官方迭代

一旦成为官方产物，扩展和绑定即可持续迭代：

- 仓库维护者负责日常治理
- 如有相关工作组，变更**应该**通过该工作组协调
- 破坏性变更需要新的标识符
- 破坏性变更需要 TSC 审查
- 维护者**应该**与 SDK 维护者协调实现更新

### 晋升至核心协议

某些扩展最终可能过渡为核心协议功能，某些自定义协议绑定也可能过渡为核心绑定。这一过程通过现有的 A2A 规范增强流程治理：

- 按照标准的规范变更流程提交提案
- 提案引用官方扩展或绑定及其采用情况
- 适用 TSC 投票及标准的法定人数和多数要求
- 并非所有扩展或绑定都适合纳入核心；许多将无限期地保持为扩展或自定义绑定

## SDK 支持

SDK 支持要求在扩展和官方自定义协议绑定之间有所不同，这反映了它们在协议生态系统中的不同角色。

**扩展**：A2A SDK 可以实现扩展。在已实现的情况下：

- 扩展必须默认禁用，需要明确选择启用
- SDK 文档应该列出支持的扩展
- SDK 维护者拥有扩展支持决策的完全自主权
- 支持扩展不是协议一致性所必需的

**官方自定义协议绑定**：A2A SDK 应当实现官方自定义协议绑定。在已实现的情况下：

- 自定义协议绑定必须默认禁用，需要明确选择启用
- SDK 文档应该列出支持的自定义协议绑定
- SDK 维护者拥有绑定支持决策的完全自主权
- 支持自定义协议绑定不是协议一致性所必需的

## 法律要求

### 许可

官方扩展和自定义协议绑定必须依据 Apache 2.0 许可提供，与 A2A 核心项目保持一致。

### 贡献者许可授予

通过向官方 A2A 扩展或自定义协议绑定仓库提交贡献，贡献者表示：

1. 他们拥有授予这些权利的合法权限
2. 该贡献是原创作品，或者他们拥有足够的权利提交它
3. 他们授予 Linux 基金会及接收方一项永久的、全球范围的、非排他性、免版税的许可，用于使用、复制、修改和分发该贡献

### 反垄断

扩展和自定义协议绑定开发者确认：

- 他们可能与其他参与者竞争
- 他们没有义务实现任何扩展或绑定
- 他们可以自由开发具有竞争力的扩展或绑定
- 作为官方扩展或绑定的地位不会构成排他性的关系
