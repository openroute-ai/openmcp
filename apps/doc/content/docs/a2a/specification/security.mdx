## 7. 认证与授权

A2A 将智能体视为标准企业应用，依赖于成熟的 Web 安全实践。身份信息在协议层处理，而非在 A2A 语义内部处理。

关于企业级安全方面的全面指南，请参阅[企业级特性](/docs/a2a/enterprise-ready)。

### 7.1. 协议安全

生产环境部署**必须**使用加密通信（基于 HTTP 的绑定使用 HTTPS，gRPC 使用 TLS）。实现**应当**使用现代 TLS 配置（推荐 TLS 1.3+）并搭配强密码套件。

### 7.2. 服务器身份验证

A2A 客户端**应当**在 TLS 握手期间，通过对照受信任的证书颁发机构（CA）验证 A2A 服务器的 TLS 证书，来验证服务器身份。

### 7.3. 客户端认证流程

1. **需求发现：**客户端通过 AgentCard 中的 `securitySchemes` 字段发现服务器所要求的认证方案。
2. **凭据获取（带外）：**客户端通过与所需认证方案对应的带外流程获取必要的凭据。
3. **凭据传输：**客户端在每个 A2A 请求中将这些凭据放入协议要求的请求头或元数据中。

### 7.4. 服务器认证职责

A2A 服务器：

- **必须**根据所提供的凭据及其声明的认证要求，认证每一个传入请求。
- **应当**使用适当的绑定特定错误码来表示认证挑战或被拒绝的认证。
- **应当**在错误响应中提供相关的认证挑战信息。

### 7.5. 服务器授权职责

认证完成后，A2A 服务器根据已认证的身份及其自身策略对请求进行授权。授权逻辑是实现特定的，并且**可以**考虑：

- 所请求的特定技能
- 任务中尝试执行的操作
- 数据访问策略
- OAuth 作用域（如适用）

### 7.6. 任务内授权

在执行任务的过程中，智能体可能需要获得授权才能执行某些操作。示例包括：

- 智能体需要 OAuth 访问令牌才能调用 API 或其他智能体
- 智能体在执行破坏性操作之前需要人工批准

在以下各节中，我们将代表已批准授权的对象称为凭据。

智能体可能有多种方式获取此授权，例如通过直接向人工发送消息。

A2A 提供了让智能体通过 `TASK_STATE_AUTH_REQUIRED` 任务状态将完成此授权的工作委托给客户端的能力。这为智能体提供了一条后备路径：将请求授权的职责移交给客户端。

#### 7.6.1 任务内授权的智能体职责

要请求客户端完成授权请求，智能体需要：

1. **必须**使用 Task 跟踪其正在执行的操作
2. **必须**将 TaskState 转换为 `TASK_STATE_AUTH_REQUIRED`
3. **必须**包含一条解释所需授权的 TaskStatus 消息，除非授权的细节已通过带外方式或扩展协商完毕

除非已通过带外方式或扩展协商了带内机制，否则智能体**必须**通过带外方式接收凭据。

如果凭据是通过带外方式接收的，在将 TaskState 设置为 `TASK_STATE_AUTH_REQUIRED` 后，智能体**应当**保持与客户端之间任何活动的响应流。智能体在收到凭据后**可以**立即继续任务处理，而不要求客户端发送后续消息。

当任务仍处于 `TASK_STATE_AUTH_REQUIRED` 时，智能体**应当**支持接收定向到该任务的消息。这使得客户端能够协商、纠正或拒绝授权请求。

#### 7.6.2 任务内授权的客户端职责

收到处于 `TASK_STATE_AUTH_REQUIRED` 的任务后，客户端应当采取某种行动来解决智能体的授权请求。

客户端可以：

- 向任务发送响应消息，以协商、纠正或拒绝授权请求。
- 联系另一个人工、智能体或服务以完成授权请求
- 通过带外或扩展约定的方式直接完成授权请求

如果客户端本身是一个正在主动处理任务的 A2A 智能体，则客户端可以进一步将授权请求委托给它的客户端，方法是将其自身的任务转换为 `TASK_STATE_AUTH_REQUIRED`。客户端**应当**遵循所有[任务内授权的智能体职责](#761-in-task-authorization-agent-responsibilities)。这样可以形成一条处于 `TASK_STATE_AUTH_REQUIRED` 状态的任务链。

客户端可能不知道智能体何时通过带外方式收到凭据并随后继续任务处理。如果客户端未与智能体建立活动的响应流，则客户端可能错过任务更新。为避免这种情况，客户端**应当**执行以下操作之一：

- 使用[订阅任务](#316-subscribe-to-task)操作订阅该任务的事件流
- 如果智能体支持，使用[创建推送通知配置](#317-create-push-notification-config)操作注册 webhook 以接收事件
- 使用[获取任务](#313-get-task)操作开始轮询该任务

#### 7.6.3 任务内授权的安全注意事项

智能体**应当**通过安全信道（如 HTTPS）带外接收任务内授权请求的凭据。这确保凭据直接提供给智能体。

带内凭据交换可以通过带外方式或使用扩展进行协商。带内凭据交换可能允许凭据跨越多个 A2A 智能体的链路传递，从而使链路中每个参与的智能体都能接触这些凭据。

如果使用带内凭据交换，建议遵循以下安全实践：

- 凭据**应当**绑定到发起请求的智能体，使只有该智能体能够使用这些凭据。这确保在 A2A 请求链中传播的凭据只能由发起请求的智能体使用。
- 包含敏感信息的凭据**应当**只能由发起请求的智能体读取，例如通过对凭据进行加密。

#### 7.6.4 任务内授权的范围

`TASK_STATE_AUTH_REQUIRED` 状态表示继续处理任务需要额外的授权。A2A 协议并未定义针对此状态所获取的授权决策或凭据的作用域、表示、有效期或撤销语义。

智能体**不得**将 `TASK_STATE_AUTH_REQUIRED` 状态转换本身视为对任何特定操作的授权。任何由此产生的授权决策或凭据的含义和作用域**必须**由智能体实现、凭据颁发者或 A2A 扩展来定义。

如果实现需要对特定操作进行授权，则其有责任定义如何标识被授权的操作，以及如何在该操作执行前检查该授权。

当任务处于 `TASK_STATE_AUTH_REQUIRED` 时获取的凭据或授权决策**不得**被假定为授权了该任务上的后续消息，除非该行为由实现、凭据颁发者或扩展明确定义。
