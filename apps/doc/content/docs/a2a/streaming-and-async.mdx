title: '流式与异步操作'
---

Agent2Agent（A2A）协议被明确设计用于处理可能不会立即完成的任务。许多 AI 驱动的操作往往是长时间运行的，涉及多个步骤，产生增量结果，或需要人工干预。A2A 提供了管理此类异步交互的机制，确保客户端无论保持持续连接还是以更断连的方式运行，都能有效收到更新。

## 使用服务器发送事件（SSE）进行流式

对于产生增量结果（例如生成很长的文档或流式传输媒体）或提供持续状态更新的任务，A2A 支持使用服务器发送事件（SSE）进行实时通信。当客户端能够与 A2A Server 保持活动中 HTTP 连接时，这种方法非常理想。

以下关键特性详细说明了 SSE 流式在 A2A 协议中的实现和管理方式：

- **服务器能力：** A2A Server 必须通过在其 Agent Card 中设置 `capabilities.streaming: true` 来表示支持流式。

- **启动流：** 客户端使用 `SendStreamingMessage` RPC 方法发送初始消息（例如提示词或命令），同时订阅该任务的更新。

- **服务器响应与连接：** 如果订阅成功，服务器以 HTTP 200 OK 状态和 `Content-Type: text/event-stream` 响应。该 HTTP 连接保持打开，以便服务器向客户端推送事件。

- **事件结构与类型：** 服务器通过该流发送事件。每个事件的 `data` 字段包含一个 JSON-RPC 2.0 Response 对象，通常是 `SendStreamingMessageResponse`。`SendStreamingMessageResponse` 的 `result` 字段包含：

    - [`Task`](/docs/a2a/specification/index)：表示工作的当前状态。
    - [`TaskStatusUpdateEvent`](/docs/a2a/specification/index)：传达任务生命周期状态的变化（例如，从 `working` 变为 `input-required` 或 `completed`）。它还提供来自智能体的中间消息。
    - [`TaskArtifactUpdateEvent`](/docs/a2a/specification/index)：投递任务生成的新产物或更新的产物。它用于分块流式传输大文件或数据结构，其中 `append` 和 `lastChunk` 等字段有助于重新组装。

- **流终止：** 当任务达到终态或中断状态（例如 `COMPLETED`、`FAILED`、`CANCELED`、`REJECTED` 或 `INPUT_REQUIRED`）时，服务器关闭流，不再发送任何更新。

- **重新订阅：** 如果客户端的 SSE 连接在任务仍处于活动状态时过早断开，客户端可以使用 `SubscribeToTask` RPC 方法尝试重新连接到流。

### 何时使用流式

使用 SSE 进行流式最适合：

- 长时间运行任务的实时进度监控。
- 增量接收较大的结果（产物）。
- 交互式、对话式交流，即时反馈或部分响应是有益的。
- 需要来自智能体的低延迟更新的应用。

- [`SubscribeToTask`](/docs/a2a/specification/index)

## 面向断连场景的推送通知

对于非常长时间运行的任务（例如持续几分钟、几小时甚至几天）或当客户端无法或不愿保持持久连接时（如移动客户端或无服务器函数），A2A 支持使用推送通知的异步更新。这使 A2A Server 能够在发生重大任务更新时主动通知客户端提供的 webhook。

以下关键特性详细说明了推送通知在 A2A 协议中的实现和管理方式：

- **服务器能力：** A2A Server 必须通过在其 Agent Card 中设置 `capabilities.pushNotifications: true` 来表示支持此功能。
- **配置：** 客户端向服务器提供 [`TaskPushNotificationConfig`](/docs/a2a/specification/index)。此配置的提供方式如下：
    - 在初始 `SendMessage` 或 `SendStreamingMessage` 请求内，或
    - 单独使用 `CreateTaskPushNotificationConfig` RPC 方法为现有任务创建。
    `TaskPushNotificationConfig` 包含 `url`（HTTPS webhook URL）、可选的 `token`（用于客户端校验）以及可选的 `authentication` 详细信息（供 A2A Server 向 webhook 进行认证）。
- **通知触发：** A2A Server 自行决定何时发送推送通知，通常是在任务达到重大状态变化时（例如，终态、`input-required` 或 `auth-required`）。
- **通知载荷：** A2A 协议将 HTTP 请求体载荷定义为 [`StreamResponse`](/docs/a2a/specification/index) 对象，与流式操作中使用的格式一致。载荷包含以下其中一项：`task`、`message`、`statusUpdate` 或 `artifactUpdate`。详细结构请参见 [推送通知载荷](/docs/a2a/specification/index)。
- **客户端操作：** 收到推送通知（并成功验证其真实性）后，客户端通常使用 `GetTask` RPC 方法，并携带通知中的 `taskId`，以检索完整、更新后的 `Task` 对象，包括任何新产物。

### 何时使用推送通知

推送通知非常适合：

- 需要几分钟、几小时甚至几天才能完成的非常长时间运行的任务。
- 无法或不愿保持持久连接的客户端，例如移动应用或无服务器函数。
- 客户端只需获知重大状态变化而非持续更新的场景。

### 协议规范参考

详细结构请参阅协议规范：

- [`CreateTaskPushNotificationConfig`](/docs/a2a/specification/index)
- [`GetTask`](/docs/a2a/specification/index)

### 客户端侧的推送通知服务

`TaskPushNotificationConfig.url` 中指定的 `url` 指向一个客户端侧的推送通知服务。该服务负责接收来自 A2A Server 的 HTTP POST 通知。其职责包括认证传入的通知、验证其相关性，并将该通知或其内容转发给适当的客户端应用逻辑或系统。

### 推送通知的安全注意事项

由于推送通知是异步的且由服务器主动向外发起，因此安全性至关重要。A2A Server（发送通知的一方）和客户端的 webhook 接收方都承担着关键职责。

#### A2A 服务器安全（向客户端 webhook 发送通知时）

- **Webhook URL 验证：** 服务器**不应该**盲目信任客户端提供的任何 URL 并发送 POST 请求。恶意客户端可能提供指向内部服务或不相关的第三方系统的 URL，从而导致服务器端请求伪造（SSRF）攻击，或充当分布式拒绝服务（DDoS）放大器。
    - **缓解策略：** 受信任域名的白名单、所有权验证（例如，质询-响应机制）以及网络控制（例如，出口防火墙）。
- **向客户端的 webhook 进行认证：** A2A Server **必须**按照 `TaskPushNotificationConfig.authentication` 中指定的方案向客户端的 webhook URL 认证自身。常见方案包括 Bearer 令牌（OAuth 2.0）、API 密钥、HMAC 签名或双向 TLS（mTLS）。

#### 客户端 webhook 接收方安全（接收来自 A2A server 的通知时）

- **认证 A2A 服务器：** webhook 端点**必须**严格验证传入通知请求的真实性，以确保它们来自合法的 A2A Server 而非冒充者。
    - **验证方法：** 验证签名/令牌（例如，对照 A2A Server 受信任的公钥验证 JWT 签名、HMAC 签名或 API 密钥验证）。同时，如果提供了 `TaskPushNotificationConfig.token`，也要对其进行验证。
- **防止重放攻击：**
    - **时间戳：** 通知**应该**包含时间戳。webhook**应该**拒绝过旧的通知。
    - **Nonce/唯一 ID：** 对于关键通知，考虑使用唯一的、一次性的标识符（例如，JWT 的 `jti` 声明或事件 ID），以防止处理重复通知。
- **安全的密钥管理与轮换：** 实施安全的密钥管理实践，包括定期密钥轮换，尤其是加密密钥。JWKS（JSON Web Key Set）等协议便于非对称密钥的轮换。

#### 非对称密钥流程示例（JWT + JWKS）

1. 客户端创建一个 `TaskPushNotificationConfig`，指定 `authentication.scheme: "Bearer"`，以及可能预期的 JWT `issuer` 或 `audience`。
2. A2A Server 在发送通知时：
    - 生成一个 JWT，并使用其私钥签名。该 JWT 包含 `iss`（签发者）、`aud`（受众）、`iat`（签发时间）、`exp`（过期时间）、`jti`（JWT ID）和 `taskId` 等声明。
    - JWT 头部指明签名算法和密钥 ID（`kid`）。
    - A2A Server 通过 JWKS 端点公开其公钥。
3. 客户端 Webhook 在收到通知时：
    - 从 Authorization 头部提取 JWT。
    - 检查 JWT 头部中的 `kid`（密钥 ID）。
    - 从 A2A Server 的 JWKS 端点获取对应的公钥（建议缓存密钥）。
    - 使用该公钥验证 JWT 签名。
    - 验证声明（`iss`、`aud`、`iat`、`exp`、`jti`）。
    - 如果提供了 `TaskPushNotificationConfig.token`，则进行检查。

这种全面、分层的推送通知安全方法有助于确保消息是真实、完整且及时的，同时保护发送方 A2A Server 和接收方客户端 webhook 基础设施。
