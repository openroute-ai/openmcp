---
title: '多租户'
---

单个 A2A 端点可以服务多个智能体或租户。A2A 协议不规定具体的路由实现——运维人员可以自由选择最适合其基础设施的方法。本文档描述了协议支持的路由机制，以及当 Agent Card 中公布了路由标识符时客户端必须遵循的规则。

## 概述

一种常见的部署模式是在单个主机或反向代理后面放置多个智能体。从外部看，这些智能体在同一个域名下可达，但每个智能体都需要被区分开来，以便请求能够投递到正确的后端。

有三种互补的方法可用：

### 1. 基于 URL 的路由（子路径）

每个智能体被分配一个不同的 URL 前缀。每个智能体的 Agent Card 在 `supportedInterfaces` 中公布自己的 `url`，因此客户端会自动向正确的路径发送请求。

"billing"（计费）智能体的 Agent Card：

```json
  ]
}
```

"support"（支持）智能体的 Agent Card：

```json
  ]
}
```

网关或反向代理将 `/billing/*` 和 `/support/*` 路由到适当的后端。这是最简单的方法，除了读取 Agent Card 之外，不需要客户端有特别的感知。

### 2. 基于认证头部的路由

当多个智能体共享同一个 URL 时，网关可以使用请求中已有的认证凭据来决定路由到哪个智能体。认证要求在 Agent Card 的 `securitySchemes` 和 `security` 字段中声明，使这种方法对客户端来说完全可以被发现。

示例：

- 一个 bearer 令牌，其声明（例如 audience 或 scope）标识目标智能体。
- 一个映射到网关配置中某个特定智能体的 API 密钥。

网关检查该凭据，并将请求转发到适当的后端，而 A2A 协议消息本身无需任何改动。

### 3. 使用 `tenant` 字段的基于报文体的路由

每个 A2A 请求消息都包含一个可选的 `tenant` 字段。这是一个**不透明字符串**，其值完全由服务器运维人员定义；协议不对其强加任何格式或语义。网关或智能体实现可以检查该字段，并将请求转发到适当的后端。

客户端对某个特定智能体应使用的 `tenant` 值，在 `supportedInterfaces` 中的 `AgentInterface` 条目中公布：

```json
  ]
}
```

**客户端要求**：客户端**必须**始终将所选 `AgentInterface` 条目中的 `tenant` 值回传到每条请求消息中。如果 `AgentInterface` 未设置 `tenant`，则请求中**必须**省略该字段。规范性规则请参见规范的[第 8.3.2 节](/docs/a2a/specification/index)。

服务器可以使用 `tenant` 字段来表示任何适合其部署的路由键——智能体标识符、工作区 slug、组织 ID 或任何其他不透明判别符。

## 组合使用多种方法

这三种方法并非互斥。例如，一个部署可以使用基于 URL 的路由区分主要产品线，同时依靠 `tenant` 字段来区分每条产品线内的各个客户。适当的组合取决于运维方的架构以及所用网关的能力。

## 发现多个智能体

当多个智能体部署在共享域名后面时，每个智能体**应该**在适当的位置发布自己的 Agent Card（参见 [智能体发现](/docs/a2a/agent-discovery)）。客户端独立获取每个智能体的卡片，并使用其中包含的 `supportedInterfaces` 信息——包括任何 `tenant` 值——与正确的智能体通信。
