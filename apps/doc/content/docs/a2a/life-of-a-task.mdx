---
title: '任务的生命周期'
---

在 Agent2Agent（A2A）协议中，交互方式多种多样。它们从简单、无状态的交换扩展到复杂、长时间运行的流程。当智能体从客户端收到消息时，它可以以下列两种方式之一响应：

- **以无状态的 `Message` 响应**：用于即时、自包含的交互。它们完成时不需要管理任何进一步的状态。
- **启动有状态的 `Task`**：智能体按照定义的生命周期运行一个 `Task`。它会报告进度，并按需请求输入，直到达到中断状态（例如 `input-required` 或 `auth-required`）或终态（例如 `completed`、`canceled`、`rejected` 或 `failed`）。

## 对相关交互进行分组

`contextId` 是一个关键标识符。它对多个 `Task` 对象和独立的 `Message` 对象进行分组。这在一系列交互中提供了连续性。

- 当客户端首次发送消息时，智能体会以一个全新的 `contextId` 响应。如果启动了任务，它将同时拥有一个 `taskId`。
- 要继续之前的交互，客户端会在后续消息中发送相同的 `contextId`。
- 客户端可以选择性地将 `taskId` 附加到后续消息上，以表明该消息是对那个特定任务的继续。

`contextId` 支持为实现共同目标而进行的协作，或者在可能同时运行的多个任务之间建立共享会话。在内部，A2A 智能体（尤其是使用 LLM 的智能体）使用 `contextId` 来管理其会话状态或 LLM 上下文。

## 智能体响应：消息或任务

选择以 `Message` 还是 `Task` 响应，取决于交互的性质和智能体的能力：

- **琐碎交互用消息**：对事务性交互使用 `Message` 对象。这些交互不需要长时间运行的处理或复杂的状态。智能体可能会使用消息，在提交 `Task` 对象之前就先就任务范围达成一致。
- **有状态交互用任务**：智能体将传入的消息映射到受支持的能力。当该能力需要在较长时期内进行大量、可跟踪的工作时，智能体会以 `Task` 对象响应。

从概念上讲，智能体在不同复杂度层级上运作：

- **仅消息型智能体**：始终以 `Message` 对象响应。它们通常不管理复杂状态或长时间运行的执行，并使用 `contextId` 将消息串联起来。这些智能体可能直接包装 LLM 调用和简单工具。
- **生成任务型智能体**：始终以 `Task` 对象响应。即使是普通的响应也被建模为已完成的任务。一旦创建了任务，智能体只返回 `Task` 对象；一旦任务完成，就不能再发送消息。这样就避免了 `Task` 与 `Message` 的抉择，但即使是简单交互也会创建已完成的任务对象。
- **混合型智能体**：同时生成 `Message` 和 `Task` 对象。这些智能体使用消息来协商智能体能力和工作范围，然后发送 `Task` 对象来跟踪执行并管理诸如 `input-required` 或错误处理等状态。换言之，`Message` 对象承载先确定应做之事的轻量级往返沟通，而一旦有需要执行和观察的承诺工作，就创建一个 `Task`。与生成任务型智能体一样，一旦创建了任务，智能体对后续消息只返回 `Task` 对象；一旦任务完成，就不能再向它发送消息。

    关于何时使用消息与任务的深入讨论，请参见 [A2A protocol: Demystifying Tasks vs Messages](https://discuss.google.dev/t/a2a-protocol-demystifying-tasks-vs-messages/255879)。

## 任务细化

客户端通常需要基于任务结果发送新请求，或细化之前任务的结果。这通过在原始任务基础上使用相同的 `contextId` 启动另一次交互来实现。客户端还通过在 `Message` 对象中提供对原始任务的引用（通过 `referenceTaskIds`）来进一步提示智能体。智能体随后以新的 `Task` 或 `Message` 响应。

## 任务的不可变性

一旦任务达到终态（completed、canceled、rejected 或 failed），它就无法重新启动。与该任务相关的任何后续交互（例如细化）必须在相同的 `contextId` 内启动新任务。这一原则带来几项好处：

- **任务的不可变性。** 客户端可以可靠地引用一个任务及其状态、产物和消息。这提供了输入到输出的清晰映射，有助于编排和可追溯性。
- **明确的工作单元。** 每个新请求、细化或后续跟进都成为一个独立的任务。这简化了记账，允许对智能体的工作进行细粒度跟踪，并使每个产物都能追溯到特定的工作单元。
- **更易于实现。** 这消除了智能体开发者在"创建新任务"和"重启现有任务"之间的歧义。

## 并行后续处理

A2A 支持并行工作，使智能体能够为在同一 `contextId` 内发送的每条后续消息创建独立的并行任务。这使客户端可以跟踪各个任务，并在前置任务完成后立即创建新的依赖任务。

例如：

- 任务 1：预订去赫尔辛基的航班。
- 任务 2：基于任务 1，预订酒店。
- 任务 3：基于任务 1，预订雪地摩托活动。
- 任务 4：基于任务 2，在酒店预订中添加水疗预约。

## 引用之前的产物

服务智能体会从被引用的任务或 `contextId` 中推断相关的产物。作为领域专家，它最适合解决歧义或发现缺失的信息。当出现歧义时，智能体会返回 `input-required` 状态，请求客户端澄清。客户端随后在其响应中指明该产物，并可以在 `Part` 元数据中添加产物引用（`artifactId`、`taskId`）。

## 跟踪产物变更

后续或细化任务通常会基于旧的产物创建新产物。跟踪这些变更，以便后续交互只使用最新版本。把它想象成一份版本历史，其中每个新产物都链接到它之前的那个产物。

客户端最适合管理这种产物链接。由客户端决定什么算作可接受的结果，并且可以接受或拒绝新版本。因此，服务智能体不应跟踪产物变更，这种链接也不属于 A2A 协议规范的组成部分。客户端应在其侧保存版本历史，并向用户展示最新的可接受版本。

为帮助客户端侧的跟踪，服务智能体在生成现有产物的细化版本时，应重用一致的 `artifact-name`。

对于后续或细化任务，客户端应指明它想要细化的确切产物——最好是它视角中的"最新"版本。如果客户端未提供产物引用，服务智能体可以：

- 尝试基于当前 `contextId` 推断预期的产物。
- 如果存在歧义或上下文不足，智能体应以 `input-required` 任务状态响应，请求客户端澄清。

    ```json
        "task": {
          "id": "task-boat-gen-123",

          "status": {
            "state": "TASK_STATE_COMPLETED"

            }
          ]
        }
      }
    }
    ```

    ```json

        }
      }
    }
    ```
