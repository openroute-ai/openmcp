本页介绍不使用 OAuth 流程的上游 MCP 认证，包括无认证、固定凭证和 AWS SigV4。OAuth 配置请参阅 [MCP OAuth](/docs/mcp-gateway/oauth)、[MCP OAuth 透传](/docs/mcp-gateway/oauth-passthrough) 或 [MCP On-Behalf-Of 认证](/docs/mcp-gateway/obo-auth)。

OpenMCP 在一次 MCP 请求中处理两个独立的认证跳转：

- **客户端到 OpenMCP：** MCP 客户端证明自己可以使用 OpenMCP 网关，通常通过 OpenMCP API 密钥。
- **OpenMCP 到上游 MCP 服务端：** OpenMCP 根据该服务端的 `auth_type` 向所选上游服务端进行认证。

MCP 服务端上的 `auth_type` 控制第二个跳转。用于网关准入的 OpenMCP API 密钥不会被复制到上游服务端。

<Callout type="info" title="Transport scope">

本页的示例涉及使用 SSE 或 Streamable HTTP 的远程 MCP 服务端。[OpenAPI 生成的 MCP 工具](/docs/mcp-gateway/openapi) 有独立的认证请求头处理。

</Callout>

## 选择非 OAuth 认证类型

对于固定的非 OAuth 凭证，选择与上游服务端要求的请求头相匹配的类型：

| `auth_type` | 你提供的内容 | 默认发送到上游的凭证 | 使用场景 |
|---|---|---|---|
| `none` | 无 | 不发送凭证 | 上游允许匿名请求，或依赖网络层面的访问控制 |
| `api_key` | 仅 API 密钥值 | `X-API-Key: <auth_value>` | 上游期望 `X-API-Key` 请求头 |
| `bearer_token` | 仅令牌 | `Authorization: Bearer <auth_value>` | 固定的不记名令牌、个人访问令牌或服务令牌 |
| `basic` | 原始 `username:password` | `Authorization: Basic <base64(username:password)>` | HTTP Basic 认证 |
| `token` | 仅令牌 | `Authorization: token <auth_value>` | 明确使用 GitHub 风格 `token` 方案的上游 |
| `authorization` | 完整的请求头值，包括其方案 | `Authorization: <auth_value>` | 自定义的授权方案；可在配置和 API 中使用 |
| `aws_sigv4` | AWS 凭证或 IAM 角色 | 每次请求生成新的 AWS SigV4 签名 | AWS Bedrock AgentCore MCP 服务端 |

## 客户端发送的内容

静态上游凭证存储在 MCP 服务端配置中。客户端不会在每次工具请求中发送上游用户名、密码或 API 密钥。

例如，无论上游服务端使用 `none`、`basic` 还是 `api_key`，客户端都可以发出相同的请求：

```http title="Client to OpenMCP"
POST /inventory/mcp HTTP/1.1
Host: openmcp.example.com
x-openmcp-api-key: Bearer sk-openmcp
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}
```

OpenMCP 对客户端进行认证，选择 `inventory` MCP 服务端，并根据该服务端的 `auth_type` 构建上游请求。以下各节展示最终发送的上游凭证。

在 `true_passthrough` 和 `oauth_delegate` 模式下，客户端需要提供上游令牌。请参阅 [MCP OAuth 透传](/docs/mcp-gateway/oauth-passthrough)。

## 非 OAuth 认证类型

### 无认证（None）

`auth_type: none` 表示认证解析器不贡献任何上游凭证。

- **行为：** 对于此认证类型，OpenMCP 不添加 `Authorization`、`X-API-Key` 或其他凭证请求头。
- **适用场景：** 上游 MCP 端点不要求应用程序凭证。常见的例子是公共 MCP 服务端，或由网络策略保护的私有端点。
- **不要用于：** 上游需要 Basic Auth、API 密钥、不记名令牌或调用方自有令牌的场景。

```yaml title="config.yaml"
mcp_servers:
  public_inventory:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "none"
```

上游请求不包含 OpenMCP 添加的任何认证凭证：

```http title="OpenMCP to upstream"
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
```

<Callout type="warn" title="Do not put credentials in the URL">

当 `auth_type` 为 `none` 时，`https://username:password@mcp.example.com/mcp` 这样的 URL 会被拒绝。OpenMCP 不会从 URL 的 userinfo 推断 Basic Auth。请从 URL 中移除凭证，并配置 [`auth_type: basic`](#basic-auth)。

</Callout>

### Basic 认证

`auth_type: basic` 将原始用户名和密码转换为标准的 HTTP Basic 请求头。

- **认证值：** 输入 `username:password`。不要对其进行 base64 编码，也不要添加 `Basic` 前缀。
- **行为：** OpenMCP 对整个值进行 base64 编码，添加 `Basic` 方案，并在每次上游请求中发送相同的服务凭证。
- **适用场景：** 上游文档要求 HTTP Basic 认证。

```yaml title="config.yaml"
mcp_servers:
  inventory:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "basic"
    auth_value: os.environ/MCP_BASIC_AUTH # value: username:password
```

对于 `MCP_BASIC_AUTH=username:password`，OpenMCP 会发送：

```http title="OpenMCP to upstream"
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
```

用户名和密码应放在 `auth_value` 中，而不是放在服务端 URL 中。

### API 密钥

`auth_type: api_key` 在 `X-API-Key` 中发送一个固定密钥。

- **认证值：** 只输入密钥值。
- **行为：** OpenMCP 在每次上游请求中发送同一个密钥。
- **适用场景：** 上游文档要求 `X-API-Key`。

```yaml title="config.yaml"
mcp_servers:
  inventory:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "api_key"
    auth_value: os.environ/INVENTORY_API_KEY
```

```http title="OpenMCP to upstream"
X-API-Key: <INVENTORY_API_KEY>
```

如果上游期望不同的请求头名称，请使用 [`static_headers`](#custom-and-forwarded-headers) 或设置 `upstream_token_header`。

### Bearer 令牌

`auth_type: bearer_token` 为固定令牌添加 `Bearer` 方案。

- **认证值：** 只输入令牌。不要添加 `Bearer` 前缀。
- **行为：** OpenMCP 在每次上游请求中发送 `Authorization: Bearer <token>`。
- **适用场景：** 上游接受固定的不记名令牌，例如服务令牌或个人访问令牌。对于必须签发、刷新、交换或由调用方提供的令牌，请参阅 [MCP OAuth](/docs/mcp-gateway/oauth)。

```yaml title="config.yaml"
mcp_servers:
  inventory:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "bearer_token"
    auth_value: os.environ/INVENTORY_TOKEN
```

```http title="OpenMCP to upstream"
Authorization: Bearer <INVENTORY_TOKEN>
```

### Token 方案

`auth_type: token` 使用小写的 `token` 授权方案。

- **认证值：** 只输入令牌。不要添加 `token` 前缀。
- **行为：** OpenMCP 发送 `Authorization: token <token>`。
- **适用场景：** 上游明确记录此方案。标准的不记名认证请使用 `bearer_token`。

```yaml title="config.yaml"
mcp_servers:
  legacy_service:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "token"
    auth_value: os.environ/LEGACY_SERVICE_TOKEN
```

```http title="OpenMCP to upstream"
Authorization: token <LEGACY_SERVICE_TOKEN>
```

### Authorization 方案

`auth_type: authorization` 按原样在 `Authorization` 请求头中发送认证值。

- **认证值：** 输入完整值，包括方案或前缀。
- **行为：** OpenMCP 不会添加、移除或更改方案。
- **适用场景：** 上游使用其他静态类型未涵盖的授权方案。该值支持在 `config.yaml` 和服务端 API 中使用，但目前未在 Admin UI 选择器中列出。

```yaml title="config.yaml"
mcp_servers:
  custom_scheme:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "authorization"
    auth_value: os.environ/CUSTOM_AUTH_HEADER # value: Custom <token>
```

```http title="OpenMCP to upstream"
Authorization: Custom <CUSTOM_AUTH_TOKEN>
```

### AWS SigV4

`auth_type: aws_sigv4` 使用 AWS Signature Version 4 对每个请求进行签名，而不是附加一个固定令牌。

- **行为：** OpenMCP 对每个请求进行哈希和签名，然后添加 AWS 所需的生成的 `Authorization`、`x-amz-date` 和临时凭证请求头。
- **适用场景：** 上游是 AWS Bedrock AgentCore MCP 服务端。
- **凭证来源：** 使用显式 AWS 凭证、boto3 凭证链，或可供 OpenMCP 扮演的 IAM 角色。

```yaml title="config.yaml"
mcp_servers:
  agentcore:
    url: "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/<url-encoded-ARN>/invocations"
    transport: "http"
    auth_type: "aws_sigv4"
    aws_role_name: os.environ/AWS_ROLE_ARN
    aws_region_name: "us-east-1"
    aws_service_name: "bedrock-agentcore"
```

有关配置和故障排查，请参阅 [MCP AWS SigV4 认证](/docs/mcp-gateway/aws-sigv4)。

## 自定义和转发的请求头

某些上游需要自定义请求头名称或不止一个固定请求头。这些设置与 `auth_type` 相互独立：

- **`static_headers`：** OpenMCP 将配置的值添加到每次上游请求中。用于自定义静态凭证、租户标识符或次级网关凭证。
- **`extra_headers`：** OpenMCP 仅将当前客户端请求中指定的请求头复制到上游。用于客户端拥有的、与请求相关的上下文。

```yaml title="config.yaml"
mcp_servers:
  custom_headers:
    url: "https://mcp.example.com/mcp"
    transport: "http"
    auth_type: "none"
    static_headers:
      X-Custom-Auth: os.environ/MCP_CUSTOM_AUTH
    extra_headers:
      - X-Tenant-ID
```

在此示例中，`none` 解析器仍然不贡献任何凭证。`X-Custom-Auth` 之所以存在，是因为它在 `static_headers` 中被单独声明。

对于调用方自有、位于 `Authorization` 中的 OAuth 不记名令牌，请使用 `true_passthrough` 或 `oauth_delegate`，而不是将其作为普通的额外请求头处理。
