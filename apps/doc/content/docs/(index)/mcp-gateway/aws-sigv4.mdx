使用 AWS SigV4 认证将 OpenMCP 连接到托管在 [AWS Bedrock AgentCore](https://docs.aws.amazon.com/bedrock/latest/userguide/agentcore.html) 上的 MCP 服务端。

## 为什么选择 SigV4？

AWS 服务使用 [Signature Version 4](https://docs.aws.amazon.com/general/latest/gr/signature-version-4.html) 对请求进行认证，这是一种按请求签名的协议，其加密签名包含请求体。这与静态请求头认证类型（`api_key`、`bearer_token` 等）的工作方式不同，后者在每次请求中发送相同的请求头。

OpenMCP 的 `aws_sigv4` 认证类型会自动处理：每个出站 MCP 请求在发送前都会使用你的 AWS 凭证进行签名。

## 快速开始

<Tabs items={["OpenMCP UI","config.yaml"]}>
<Tab>

1. 导航到 **MCP Servers**，然后点击 **Add New MCP Server**
2. 将传输方式设置为 **Streamable HTTP**
3. 选择 **AWS SigV4** 作为认证类型
4. 填写你的 AWS 凭证：

<img src="/images/docs/mcp-gateway/mcp_aws_sigv4_ui.png" style={{width: '80%', display: 'block', margin: '0'}} />

<br/>

| 字段 | 是否必填 | 说明 |
|-------|----------|-------------|
| **AWS Region** | 是 | 用于 SigV4 签名的 AWS 区域（例如 `us-east-1`） |
| **AWS Service Name** | 否 | 默认为 `bedrock-agentcore` |
| **AWS Access Key ID** | 否 | 留空时回退到 boto3 凭证链 |
| **AWS Secret Access Key** | 否 | 提供 Access Key ID 时必填 |
| **AWS Session Token** | 否 | 仅临时 STS 凭证需要 |
| **AWS Role ARN** | 否 | 用于 STS AssumeRole 的 IAM 角色 ARN（例如 `arn:aws:iam::123456789012:role/MyRole`）。设置后，OpenMCP 会在签名前扮演该角色 |
| **AWS Session Name** | 否 | AssumeRole 调用的会话名称——会出现在 CloudTrail 中。省略时自动生成 |

创建后，OpenMCP 将使用 SigV4 对每个出站 MCP 请求进行签名。该服务端的工具会自动出现在 MCP Tools 列表中。

**编辑凭证：** 编辑现有的 SigV4 服务端时，请将凭证字段留空以保留当前值。只有你填写的字段才会被更新。

### 1. 设置 AWS 凭证

```bash
export AWS_ACCESS_KEY_ID="AKIA..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_REGION_NAME="us-east-1"
```

### 2. 将你的 AgentCore MCP 服务端添加到 config.yaml

```yaml title="config.yaml" showLineNumbers
model_list:
  - model_name: {{openai_large}}
    openmcp_params:
      model: openai/{{openai_large}}
      api_key: os.environ/OPENAI_API_KEY

mcp_servers:
  my_agentcore_mcp:
    url: "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/<url-encoded-ARN>/invocations"
    transport: "http"
    auth_type: "aws_sigv4"
    aws_role_name: os.environ/AWS_ROLE_ARN          # IAM role to assume (recommended)
    aws_session_name: "openmcp-prod"                 # optional — for CloudTrail auditing
    aws_region_name: "us-east-1"
    aws_service_name: "bedrock-agentcore"
```

<Callout type="info" title="URL encoding">

AgentCore 运行时 ARN 必须对 `url` 字段进行 URL 编码。例如：

```
arn:aws:bedrock-agentcore:us-east-1:123456789012:runtime/my-mcp-server
```

将会变成：

```
arn%3Aaws%3Abedrock-agentcore%3Aus-east-1%3A123456789012%3Aruntime%2Fmy-mcp-server
```

</Callout>

### 3. 启动代理

```bash
openmcp --config config.yaml
```

## 使用 MCP 工具

配置完成后，你的 AgentCore MCP 工具就可以像其他任何 MCP 服务端一样通过 OpenMCP 使用：

```bash title="List available tools"
curl http://localhost:4000/mcp-rest/tools/list \
  -H "Authorization: Bearer sk-1234"
```

```bash title="Call a tool"
curl http://localhost:4000/mcp-rest/tools/call \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-1234" \
  -d '{
    "server_id": "my_agentcore_mcp",
    "name": "my_agentcore_mcp-your_tool_name",
    "arguments": {"key": "value"}
  }'
```

工具命名、`server_id` 格式和常见错误请参阅 [MCP REST API](/docs/mcp-gateway/rest-api)。

## 配置参考

| 字段 | 是否必填 | 说明 |
|-------|----------|-------------|
| `url` | 是 | AgentCore MCP 服务端 URL（带 URL 编码的 ARN） |
| `transport` | 是 | 必须为 `"http"` |
| `auth_type` | 是 | 必须为 `"aws_sigv4"` |
| `aws_access_key_id` | 否 | AWS 访问密钥。支持 `os.environ/VAR_NAME`。省略时回退到 boto3 凭证链 |
| `aws_secret_access_key` | 否 | AWS 秘密访问密钥。支持 `os.environ/VAR_NAME`。省略时回退到 boto3 凭证链 |
| `aws_region_name` | 是 | AWS 区域（例如 `us-east-1`） |
| `aws_service_name` | 否 | 用于签名的 AWS 服务名称。默认为 `bedrock-agentcore` |
| `aws_session_token` | 否 | 用于临时凭证的 AWS 会话令牌。支持 `os.environ/VAR_NAME` |
| `aws_role_name` | 否 | 用于 STS AssumeRole 的 IAM 角色 ARN。支持 `os.environ/VAR_NAME`。设置后，OpenMCP 在签名前会调用 `sts:AssumeRole` 获取临时凭证 |
| `aws_session_name` | 否 | AssumeRole 调用的会话名称（会出现在 CloudTrail 中）。省略时自动生成。支持 `os.environ/VAR_NAME` |

## 工作原理

OpenMCP 使用一个 `httpx.Auth` 子类（`MCPSigV4Auth`），它挂接在 HTTP 请求生命周期中：

1. 对于每个出站 MCP 请求，认证处理器计算请求体的 SHA-256 哈希
2. 它使用你的 AWS 凭证、请求 URL、请求头和请求体哈希创建 SigV4 签名
3. 签名后的 `Authorization` 和 `x-amz-date` 请求头会被添加到请求中
4. AWS 验证签名并处理 MCP 请求

这一切会自动完成，无需手动管理令牌。

## 使用临时凭证（STS）

如果你使用 AWS STS 临时凭证（例如来自 IAM 角色或 SSO），请包含会话令牌：

```yaml title="config.yaml with STS credentials" showLineNumbers
mcp_servers:
  my_agentcore_mcp:
    url: "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/<url-encoded-ARN>/invocations"
    transport: "http"
    auth_type: "aws_sigv4"
    aws_access_key_id: os.environ/AWS_ACCESS_KEY_ID
    aws_secret_access_key: os.environ/AWS_SECRET_ACCESS_KEY
    aws_session_token: os.environ/AWS_SESSION_TOKEN
    aws_region_name: "us-east-1"
    aws_service_name: "bedrock-agentcore"
```

## 使用 IAM 角色扮演（AssumeRole）

对于通过 IAM 角色进行认证（例如 EKS pod 角色、EC2 实例配置文件）的生产环境，你可以配置 `aws_role_name`，让 OpenMCP 在签名 MCP 请求之前调用 `sts:AssumeRole`：

```yaml title="config.yaml with AssumeRole" showLineNumbers
mcp_servers:
  my_agentcore_mcp:
    url: "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/<url-encoded-ARN>/invocations"
    transport: "http"
    auth_type: "aws_sigv4"
    aws_role_name: "arn:aws:iam::123456789012:role/BedrockAgentCoreRole"
    aws_session_name: "openmcp-prod"    # optional
    aws_region_name: "us-east-1"
    aws_service_name: "bedrock-agentcore"
```

OpenMCP 使用环境凭证（pod 角色、实例配置文件或环境变量）调用 `sts:AssumeRole`，然后使用扮演角色获得的临时凭证对 MCP 请求进行签名。

你还可以将 `aws_role_name` 与显式访问密钥结合使用。这些密钥随后将用作 AssumeRole 调用的源身份：

```yaml title="config.yaml with AssumeRole + explicit source keys" showLineNumbers
mcp_servers:
  my_agentcore_mcp:
    url: "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/<url-encoded-ARN>/invocations"
    transport: "http"
    auth_type: "aws_sigv4"
    aws_role_name: os.environ/AWS_ROLE_ARN
    aws_access_key_id: os.environ/AWS_ACCESS_KEY_ID
    aws_secret_access_key: os.environ/AWS_SECRET_ACCESS_KEY
    aws_region_name: "us-east-1"
```

<Callout type="info">

对于大多数 Kubernetes 部署，你只需要 `aws_role_name` 和 `aws_region_name`；pod 的 IAM 角色会自动提供源凭证。

</Callout>

## 故障排查

### 来自 AWS 的 403 Forbidden

- 验证你的 AWS 凭证有效且未过期
- 检查 `aws_region_name` 是否与 AgentCore URL 中的区域匹配
- 确保 `aws_service_name` 设置为 `bedrock-agentcore`
- 如果使用 STS 凭证，请确认 `aws_session_token` 已设置且未过期

### AssumeRole 出现 AccessDenied

如果你在设置 `aws_role_name` 时收到 `AccessDenied`：

- 验证角色 ARN 是否正确
- 检查目标角色上的信任策略是否允许你的源身份扮演该角色
- 如果在 EKS 上运行，请确保 pod 的服务账户注入了正确的 IAM 角色
- 在 CloudTrail 中检查失败的 `sts:AssumeRole` 调用，查看确切错误

### 启动时的健康检查错误

已启用 SigV4 认证的 MCP 服务端会跳过代理启动时的标准健康检查。这是预期行为，代理在工具被调用时仍会正确地签名请求。

### “botocore not found”错误

安装 `botocore` 包：

```bash
uv add botocore
```

`botocore` 用于 SigV4 凭证处理，使用 `aws_sigv4` 认证时是必需的。
