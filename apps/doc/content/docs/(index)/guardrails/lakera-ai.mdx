**支持的端点：** Lakera v2 集成仅支持 **chat completions** 端点（`/v1/chat/completions`）。它不支持 Responses API、`/v1/messages`、MCP、A2A 或其他代理端点。

## 快速开始
### 1. 在 OpenMCP config.yaml 中定义护栏

在 `guardrails` 部分定义你的护栏

```yaml showLineNumbers title="openmcp config.yaml"
model_list:
  - model_name: {{openai_small}}
    openmcp_params:
      model: openai/{{openai_small}}
      api_key: os.environ/OPENAI_API_KEY

guardrails:
  - guardrail_name: "lakera-guard"
    openmcp_params:
      guardrail: lakera_v2  # supported values: "aporia", "bedrock", "lakera"
      mode: "during_call"
      api_key: os.environ/LAKERA_API_KEY
      api_base: os.environ/LAKERA_API_BASE
  - guardrail_name: "lakera-pre-guard"
    openmcp_params:
      guardrail: lakera_v2  # supported values: "aporia", "bedrock", "lakera"
      mode: "pre_call"
      api_key: os.environ/LAKERA_API_KEY
      api_base: os.environ/LAKERA_API_BASE
  - guardrail_name: "lakera-monitor"
    openmcp_params:
      guardrail: lakera_v2
      mode: "pre_call"
      on_flagged: "monitor"  # Log violations but don't block
      api_key: os.environ/LAKERA_API_KEY
      api_base: os.environ/LAKERA_API_BASE
  
```

#### `mode` 支持的取值

- `pre_call` 在 **LLM 调用之前** 对**输入**运行
- `post_call` 在 **LLM 调用之后** 对**输入和输出**运行
- `during_call` 在 **LLM 调用期间** 对**输入**运行。与 `pre_call` 相同，但与 LLM 调用并行运行。  响应在护栏检查完成前不会返回

### 2. 启动 OpenMCP 网关

```shell
openmcp --config config.yaml --detailed_debug
```

## 支持的参数

```yaml
guardrails:
  - guardrail_name: "lakera-guard"
    openmcp_params:
      guardrail: lakera_v2  # supported values: "aporia", "bedrock", "lakera"
      mode: "during_call"
      api_key: os.environ/LAKERA_API_KEY
      api_base: os.environ/LAKERA_API_BASE
      ### OPTIONAL ### 
      # project_id: Optional[str] = None,
      # payload: Optional[bool] = True,
      # breakdown: Optional[bool] = True,
      # metadata: Optional[Dict] = None,
      # dev_info: Optional[bool] = True,
      # on_flagged: Optional[str] = "block",  # "block", "monitor", or "inject_system_message"
      # advisory_system_message: Optional[str] = None,  # custom template, only used with on_flagged: "inject_system_message"
      # skip_system_message_in_guardrail: Optional[bool] = None,  # exclude role: system from Lakera's inspection
      # skip_tool_message_in_guardrail: Optional[bool] = None,  # exclude role: tool from Lakera's inspection
```

- `api_base`: (Optional[str]) Lakera 集成的基础地址。默认为 `https://api.lakera.ai`
- `api_key`: (str) Lakera 集成的 API 密钥。
- `project_id`: (Optional[str]) 相关项目的 ID
- `payload`: (Optional[bool]) 当为 true 时，响应会返回一个 payload 对象，其中包含检测到的任何 PII、粗俗词汇或自定义检测器正则匹配项，以及它们在内容中的位置。
- `breakdown`: (Optional[bool]) 当为 true 时，响应会返回按策略定义的已运行检测器的细分列表，以及每个检测器是否检测到了内容。
- `metadata`: (Optional[Dict]) 元数据标签可以附加到筛选请求上，作为一个可包含任意键值对的对象。
- `dev_info`: (Optional[bool]) 当为 true 时，响应会返回一个包含 Lakera Guard 构建相关开发者信息的对象。
- `on_flagged`: (Optional[str]) 当内容被标记时要采取的动作。默认为 `"block"`。
  - `"block"`: 检测到违规时抛出 HTTP 400 异常（默认行为）
  - `"monitor"`: 记录违规但允许请求继续。适用于在拦截合法请求之外调整安全策略。
  - `"inject_system_message"`: 向请求追加一条建议性系统消息，并让真正的 LLM 调用继续执行（HTTP 200），而不是拦截或静默放行。其工作原理和限制见下文[建议模式](#advisory-mode)。
- `advisory_system_message`: (Optional[str]) 自定义建议消息模板，仅当 `on_flagged: "inject_system_message"` 时使用。必须是包含真实 `{reason}` 占位符的有效 `str.format()` 字符串（转义的 `{{reason}}` 会被拒绝）；模板无效会在配置护栏时报错，而不是在第一个被标记的请求时才报错。未设置时默认为内置的通用消息。
- `skip_system_message_in_guardrail`: (Optional[bool]) 将 `role: system` 消息从发送给 Lakera 检查的内容中排除。LLM 仍会收到完整的对话；只是过滤掉 Lakera 看到的视角。如果未设置，则回退到全局的 `openmcp_settings.skip_system_message_in_guardrail`。有关全局设置和管理后台 UI 控件，请参阅[护栏快速开始](./quick_start#skip-system-messages-in-guardrail-evaluation)。
- `skip_tool_message_in_guardrail`: (Optional[bool]) 与上一条相同，用于 `role: tool` 消息（工具调用结果）。如果未设置，则回退到 `openmcp_settings.skip_tool_message_in_guardrail`。请参阅[护栏快速开始](./quick_start#skip-tool-messages-in-guardrail-evaluation)。

与大多数通过对原始请求运行直接钩子（direct hook）的护栏不同，Lakera v2 会直接遵循这两个 skip 标志；大多数直接钩子护栏都不会这样做。有关各护栏的完整情况，请参阅[skip 标志适用范围](./quick_start#where-the-skip-flags-apply)。

就地遮罩（masking）会同时保留两个 skip 标志以及消息上的所有其他字段（工具消息的 `tool_call_id`、助手消息的 `tool_calls`、`name`、`cache_control`，等等）：只有消息自身的 `content` 会被重写，被任一 skip 标志排除的消息会原封不动地保留在其原始位置，而不是被丢弃。在两种更窄的情况下，Lakera v2 仍会降级为拦截而不是遮罩，因为此时脱敏结果无法安全地写回：当消息带有非字符串（多模态）内容时，或者当请求将 chat completions 的 `messages` 与 Responses API 的 `input` 字段组合在一起、或带有 Responses API 的 `instructions` 字段时，因为在这种情况下没有可以安全作为遮罩目标的单一字段。

## 建议模式

`on_flagged: "inject_system_message"` 适用于容易产生误报的检测器，例如提示词注入启发式规则会在合法的指令性语言上误触发，这时操作者希望由 LLM 自己来权衡标记是否为真，而不是硬性拦截每个被标记的请求，或在完全没有提示信号的情况下直接放行。

```yaml showLineNumbers title="openmcp config.yaml"
guardrails:
  - guardrail_name: "lakera-advisory"
    openmcp_params:
      guardrail: lakera_v2
      mode: "pre_call"
      on_flagged: "inject_system_message"
      # advisory_system_message: "Custom template with a {reason} placeholder"
      api_key: os.environ/LAKERA_API_KEY
      api_base: os.environ/LAKERA_API_BASE
```

当发生标记时，护栏会向请求追加一条系统消息，真正的 LLM 调用会正常继续（HTTP 200）。使用默认模板时，该消息内容如下：

```
The user's latest message was flagged for {reason} by a content safety guardrail. This may be a false positive. Use your judgment: respond helpfully if the request is legitimate, or decline if it is not.
```

`{reason}` 会从 Lakera 自己的检测器细分结果中填充，例如"潜在的提示词注入尝试"、"个人身份信息"或"违反策略的内容"。设置 `advisory_system_message` 可以覆盖措辞，但要在模板中保留真实的 `{reason}` 占位符。

对于 Responses API 请求，当存在 `instructions` 字段时，建议消息会被追加到 `instructions` 而不是 `input`：`instructions` 是开发者设置的、享有特权的系统级字段，而 `input` 由调用方控制，否则调用方可能在其中包含让模型忽略追加在末端的警告的文本。`instructions` 会以同样的方式被检查，因此源于该处的标记仍会正确地触发建议消息。

仅包含 PII 的标记会被就地遮罩，而不是接收建议消息：没有必要为了传递一条建议说明而向模型展示原始的 PII，遮罩本身就已经解决了问题。建议消息只保留给建议模式无法以其他方式解决的标记，例如提示词注入启发式规则。

建议模式有两个与护栏在请求生命周期中运行时机相关的限制：

- **不支持 `mode: "during_call"`。** `during_call` 会与 LLM 请求并发运行护栏，两者之间没有屏障，因此在请求发出之前无法可靠地找到追加建议消息的时机。如果配置的 `mode` 包含 `during_call`，则在配置护栏时会抛出错误。请改用 `mode: "pre_call"`。
- **`mode: "post_call"` 的行为与 `on_flagged: "monitor"` 相同。** 当 post-call 护栏运行时，LLM 已经生成了响应，因此已经没有可以注入建议消息的地方。标记会被记录，响应会原样返回。
