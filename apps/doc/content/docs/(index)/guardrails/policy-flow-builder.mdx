策略流程构建器让你可以利用**条件执行**设计护栏流水线。护栏不再独立运行，而是被串联成有序的步骤，并控制当每个护栏**通过**、**未通过策略检查**（内容干预）或遇到**技术错误**（例如超时、提供方不可达、护栏缺失）时会发生什么。

它支持的两种模式是：**护栏回退**（当一个护栏失败时尝试另一个护栏）和**重试同一护栏**（如果护栏失败则再次运行同一个护栏，例如用于处理瞬时错误）。借助 **`on_error`**，你可以将**技术**失败与**策略**失败区分对待，例如当主 API 出错时回退到另一个提供方，同时仍阻止被标记的内容。

## 何时使用流程构建器

| 方式 | 适用场景 |
|----------|----------|
| **简单策略**（`guardrails.add`） | 所有护栏并行运行；任何失败都会阻止请求。 |
| **流程构建器**（pipeline） | 护栏按顺序运行；你为每个步骤选择动作（next、block、allow、自定义响应）。 |

当你需要以下能力时，使用流程构建器：

- **护栏回退** — 使用 `on_fail: next` 在某个护栏失败时尝试另一个护栏（例如快速过滤器 → 更严格的过滤器）
- **重试同一护栏** — 将同一护栏添加为多个步骤；如果失败，`on_fail: next` 会移动到下一个步骤，它可以是同一个护栏（对于瞬时 API 错误或速率限制很有用）
- **条件路由** — 例如，如果快速护栏失败，运行更高级的护栏而不是立即阻止
- **自定义响应** — 当护栏失败时返回特定消息，而不是通用的阻止
- **数据链式传递** — 将修改后的数据（例如 PII 掩码内容）从一个步骤传递到下一步
- **精细控制** — 每个步骤在通过与失败时有不同的动作
- **技术错误路由** — 独立于 `on_fail` 设置 `on_error`，以便中断或超时可以**放行**、**阻止**、**进入下一步**或返回**自定义响应**，而不会与内容违规混淆

## 概念

### 流水线

一个流水线包含：

- **模式**：`pre_call`（LLM 之前）或 `post_call`（LLM 之后）
- **步骤**：有序的护栏步骤列表

### 结果：pass、fail 和 error

每次步骤运行都会产生三种结果之一：

| 结果 | 含义 | 典型原因 |
|--------|---------|----------------|
| **pass** | 护栏完成且未阻止 | 内容被允许，或数据被修改并返回 |
| **fail** | 策略干预 | 护栏提出了干预（例如标记的内容、被阻止的请求） |
| **error** | 技术失败 | 超时、网络错误、护栏未注册或其他非干预类异常 |

`on_pass` 和 `on_fail` 分别适用于 **pass** 和 **fail**。**`on_error`** 仅适用于 **error**。如果省略 `on_error`，流水线会对 error 结果使用 **`on_fail`**（向后兼容）。

### 步骤动作

对于每个步骤，你为 **pass**、**fail** 以及可选的 **error** 选择一个动作。允许的值有：`next`、`allow`、`block`、`modify_response`。

| 动作 | 描述 |
|--------|-------------|
| **下一步**（`next`） | 继续到流水线中的下一个护栏 |
| **放行**（`allow`） | 停止流水线并允许请求继续 |
| **阻止**（`block`） | 停止流水线并阻止请求 |
| **自定义响应**（`modify_response`） | 返回自定义消息而不是默认的阻止 |

### 步骤选项

| 字段 | 类型 | 描述 |
|-------|------|--------------|
| `guardrail` | `string` | 要运行的护栏名称 |
| `on_pass` | `string` | 结果为 **pass** 时的动作：`next`、`allow`、`block`、`modify_response` |
| `on_fail` | `string` | 结果为 **fail**（策略干预）时的动作：`next`、`allow`、`block`、`modify_response` |
| `on_error` | `string`（可选） | 结果为 **error**（技术性）时的动作。如果省略，**error** 使用 `on_fail`。 |
| `pass_data` | `boolean` | 将修改后的请求数据（例如 PII 掩码）转发到下一步 |
| `modify_response_message` | `string` | 使用 `modify_response` 动作时的自定义消息 |

## 使用流程构建器（UI）

1. 进入 OpenMCP Admin UI 中的 **Policies**
2. 点击 **+ Create New Policy** 或在现有策略上点击 **Edit**
3. 选择 **Flow Builder**（替代简单表单）
4. 设计你的流程：
   - **Trigger** — 传入的 LLM 请求（当策略匹配时运行）
   - **Steps** — 添加护栏；为每个步骤设置 **ON PASS**、**ON FAIL** 和 **ON API FAILURE** / **ON ERROR**（当 **ON API FAILURE** 未设置时，技术错误遵循 **ON FAIL**）
   - **End** — 当流水线放行请求时，请求继续到 LLM
5. 使用步骤之间的 **+** 插入另一个护栏步骤（用于回退、重试或更严格的二次检查）
6. 在保存之前使用 **Test Pipeline** 运行示例消息
7. 点击 **Save Policy**（或 **Save**）创建或更新策略

## 配置（YAML）

在你的策略配置中定义流水线：

```yaml showLineNumbers title="config.yaml"
guardrails:
  - guardrail_name: pii_masking
    openmcp_params:
      guardrail: presidio
      mode: pre_call

  - guardrail_name: prompt_injection
    openmcp_params:
      guardrail: lakera
      mode: pre_call

policies:
  my-pipeline-policy:
    description: "PII mask first, then check for prompt injection"
    guardrails:
      add:
        - pii_masking
        - prompt_injection
    pipeline:
      mode: pre_call
      steps:
        - guardrail: pii_masking
          on_pass: next
          on_fail: block
          pass_data: true
        - guardrail: prompt_injection
          on_pass: allow
          on_fail: block

policy_attachments:
  - policy: my-pipeline-policy
    scope: "*"
```

## 回退与重试

### 护栏回退

使用 `on_fail: next` 在某个护栏失败时回退到另一个护栏。先运行轻量级护栏；如果它失败，则升级到更严格或不同的提供方：

```yaml
policies:
  fallback-policy:
    guardrails:
      add:
        - fast_content_filter
        - strict_content_filter
    pipeline:
      mode: pre_call
      steps:
        - guardrail: fast_content_filter
          on_pass: allow
          on_fail: next
        - guardrail: strict_content_filter
          on_pass: allow
          on_fail: block
```

如果 `fast_content_filter` 通过 → 放行。如果失败 → 运行 `strict_content_filter`；通过 → 放行，失败 → 阻止。

### 重试同一护栏

将同一护栏添加为多个步骤以在失败时重试。对于瞬时错误（API 超时、速率限制）很有用：

```yaml
policies:
  retry-policy:
    guardrails:
      add:
        - lakera_prompt_injection
    pipeline:
      mode: pre_call
      steps:
        - guardrail: lakera_prompt_injection
          on_pass: allow
          on_fail: next
        - guardrail: lakera_prompt_injection
          on_pass: allow
          on_fail: block
```

第一次尝试通过 → 放行。第一次尝试失败 → 重试同一护栏；第二次通过 → 放行，第二次失败 → 阻止。

## 技术错误与策略失败（`on_error`）

当你希望对**API/基础架构问题**的处置不同于**内容策略**违规时，使用 **`on_error`**。

- **`on_fail`** — 当护栏**干预**时运行（例如有毒内容、检测到 PII）。
- **`on_error`** — 当步骤以 **error** 结束时运行（超时、连接失败、护栏未加载等）。如果省略 `on_error`，**error** 结果使用 **`on_fail`**。

示例：对不良内容进行阻止，但如果主扫描器宕机，则回退到第二个护栏，而不是阻止每个请求：

```yaml
policies:
  error-fallback-policy:
    guardrails:
      add:
        - primary_scanner
        - backup_scanner
    pipeline:
      mode: pre_call
      steps:
        - guardrail: primary_scanner
          on_pass: allow
          on_fail: block
          on_error: next
        - guardrail: backup_scanner
          on_pass: allow
          on_fail: block
          on_error: allow
```

如果 `primary_scanner` 出错 → 运行 `backup_scanner`。如果 `backup_scanner` 出错 → 放行请求（如果你更倾向于故障关闭，请将 `on_error` 设置为 `block`）。

## 示例：失败时的自定义响应

返回品牌化消息而不是通用的阻止：

```yaml
policies:
  branded-block-policy:
    guardrails:
      add:
        - pii_detector
    pipeline:
      mode: pre_call
      steps:
        - guardrail: pii_detector
          on_pass: allow
          on_fail: modify_response
          modify_response_message: "Your message contains sensitive information. Please remove PII and try again."
```

## 测试流水线（API）

在附加流水线之前，用示例消息测试它：

```bash
curl -X POST "http://localhost:4000/policies/test-pipeline" \
  -H "Authorization: Bearer <your_api_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "pipeline": {
      "mode": "pre_call",
      "steps": [
        {
          "guardrail": "pii_masking",
          "on_pass": "next",
          "on_fail": "block",
          "pass_data": true
        },
        {
          "guardrail": "prompt_injection",
          "on_pass": "allow",
          "on_fail": "block"
        }
      ]
    },
    "test_messages": [
      {"role": "user", "content": "What is 2+2?"},
      {"role": "user", "content": "My SSN is 123-45-6789"}
    ]
  }'
```

响应包含每个步骤的结果（pass/fail/error）、采取的动作和时间。

## 流水线与简单策略

当策略具有 `pipeline` 时，流水线定义了执行顺序和动作。`guardrails.add` 列表必须包含流水线步骤中使用的所有护栏。

| 策略类型 | 执行 |
|-------------|-----------|
| 简单策略（仅 `guardrails.add`） | 所有护栏运行；任何失败都会阻止 |
| 流水线（存在 `pipeline`） | 步骤按顺序运行；动作控制流程 |
