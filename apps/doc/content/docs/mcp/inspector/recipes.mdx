## 连接 stdio 与 HTTP 服务端

### stdio

stdio 服务端是 Inspector 生成的一个进程。所有位置参数都是命令行：

```bash
mcp-inspector node build/index.js -- --verbose --config /etc/myserver.conf
```

把 `--` 放在任何给服务端的参数之前。没有分隔符的话，`--verbose` 会被 Inspector 解析，永远不会到达服务端。

用 `-e` 给进程环境变量，用 `--cwd` 给工作目录：

```bash
mcp-inspector -e API_KEY=abc123 -e REGION=us-east-1 --cwd ~/projects/my-server \
  node build/index.js
```

服务端的 `stderr` 会落入 **Console** 选项卡（web）或 Console 选项卡（`o`，TUI），这是大多数 stdio 服务端放诊断信息的地方，所以当连接毫无可见理由失败时，先检查这里。

### HTTP 和 SSE

```bash
mcp-inspector --server-url https://api.example.com/mcp --transport http \
  --header "X-Tenant: acme"
```

`--transport` 接受 `http`（Streamable HTTP）和 `sse`。如果服务端受保护，参见[授权](/docs/mcp/tools/inspector/authorization)：无需预先配置，因为当服务端回答 `401` 时，Inspector 会运行那里描述的 OAuth 流程并重试连接。

对于 HTTP 服务端，还要确定它的[协议时代](/docs/mcp/tools/inspector/protocol-eras)。默认是 `legacy`；在 Server Settings（或 catalog 文件里的 `protocolEra`）中设置为 `modern` 或 `auto` 来演练 2026-07-28 的行为。

## 导入现有客户端配置

在 Servers 屏幕上，**Add Servers（添加服务端）** 可以导入你已经在别处配置好的 MCP 服务端，而不是重新输入一遍。它直接解析 Claude Desktop、Cursor、Cline 和 VS Code 客户端配置，也读取服务端自己的 [MCP Registry](/docs/mcp/registry/about) `server.json`。

导入会合并到活动 [catalog](/docs/mcp/tools/inspector/configuration#choosing-servers)（Inspector 可写的服务端列表）中，因此已有条目不会被覆盖。如果你根本不想动你的 catalog，改用以只读方式对着外部文件启动：

```bash
mcp-inspector --config ~/Library/Application\ Support/Claude/claude_desktop_config.json
```

`--config` 保证文件被原样提供，绝不会被写入、播种或迁移。

## 审核一个 MCP App

[MCP Apps](/docs/mcp/extensions/apps/overview) 是携带 UI 组件的工具。对于自动化审核方（CI 或 agent），凡是返回 JSON 的检查都用 CLI，只为了检查渲染出的组件时才打开浏览器。

<Steps>
  <Step>

### 不调用工具即可探测安全姿态

```bash
mcp-inspector --cli --transport http --server-url https://example.com/mcp \
  --method tools/call --tool-name <tool> --app-info
```

stdout 上一行 JSON；工具有 app 则退出码 `0`，没有则 `2`，因此 `&&` 链可以短路：

```json
{
  "hasApp": true,
  "toolName": "get_pros",
  "resourceUri": "ui://pros/view.html",
  "csp": { "connectDomains": ["https://api.example.com"] },
  "permissions": { "clipboard": false },
  "prefersBorder": true,
  "resourceMimeType": "text/html"
}
```

`csp` 和 `permissions`（以及资源声明了 `domain` 时的 `domain`）位于 UI **资源**上而不是工具上，因此 `--app-info` 读取的是那个资源。工具永远不会被调用。

  

</Step>

<Step>

### 拿到完整的结果 payload，仍然不用浏览器

```bash
mcp-inspector --cli --transport http --server-url https://example.com/mcp \
  --method tools/call --tool-name <tool> --tool-args-json '{"zip":"10001"}' --format json
```

  

</Step>

<Step>

### 启动一次仅 loopback 的 web Inspector

```bash
TOKEN="$(openssl rand -hex 24)"
HOST=127.0.0.1 CLIENT_PORT=6274 MCP_SANDBOX_PORT=6275 \
MCP_AUTO_OPEN_ENABLED=false MCP_INSPECTOR_API_TOKEN="$TOKEN" \
mcp-inspector --web &
```

固定 `MCP_SANDBOX_PORT` 在这里很重要：应用的 UI 由另一个默认动态的沙箱端口提供，你的自动化需要一个固定地址才能访问它。

  

</Step>

<Step>

### 用一条深度链接导航到渲染出的组件

```
http://127.0.0.1:6274/?serverUrl=<encoded url>&transport=http&autoConnect=<TOKEN>&openApp=<tool>&appArgs=<base64url(JSON)>&autoOpen=<TOKEN>
```

`appArgs` 是工具的参数，用 base64url 编码的 JSON 表示，每个深度链接参数的说明见[深度链接](/docs/mcp/tools/inspector/web#deep-links)。`autoConnect` 和 `autoOpen` 必须都等于会话令牌，因为 `autoOpen` 会直接从 URL 触发一次工具调用，需要与 `autoConnect` 相同的门禁。

  

</Step>

<Step>

### 等待确定性信号，而不是 sleep

Apps 屏幕暴露了一个稳定的自动化契约。轮询以下属性，而不是 sleep：

| 选择器                            | 属性         | 值                                                                                                  |
| ----------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------- |
| `[data-testid="apps-form"]`         | `data-app-status` | `ready`（失败时，`data-app-error` 携带原因）                                               |
| `[data-testid="connection-status"]` | `data-status`     | `connecting`，然后是 `connected` 或 `error`（`data-error-message` 有详细信息）                         |
| `[data-testid="connection-status"]` | `data-deeplink`   | `parsed`、`rejected` 或 `none`（`none` 表示没有给出深度链接，`rejected` 表示有一个被拒绝） |

  

</Step>

</Steps>

## Docker

一个容器镜像已发布到 GitHub Container Registry，支持 `linux/amd64` 和 `linux/arm64`：

```bash
docker run --rm -p 6274:6274 ghcr.io/modelcontextprotocol/inspector
```

从容器日志中读取[会话令牌](/docs/mcp/tools/inspector/web#the-session-token)，或用 `-e MCP_INSPECTOR_API_TOKEN=<value>` 固定它。

镜像默认 `--web`，绑定 `0.0.0.0:6274`、关闭浏览器自动打开，并以非 root 用户运行。它设置 `DANGEROUSLY_BIND_ALL_INTERFACES=true`，因为容器必须绑定通配符地址才能通过 `-p` 被访问到。

它的 `HEALTHCHECK` 探测 web UI，因此运行 `--cli` 或 `--tui`（两者都没有 web 服务器）时要加 `--no-healthcheck`。下面的 `<target>` 是一个[临时目标](/docs/mcp/tools/inspector/configuration#ad-hoc-targets)：位置参数 stdio 命令，或 `--server-url <url> --transport http`。

```bash
docker run --rm --no-healthcheck ghcr.io/modelcontextprotocol/inspector --cli <target> --method tools/list
```

<Callout type="warn">
  **如果你重映射了发布的端口，请设置 `ALLOWED_ORIGINS`。** 用 `-p
  8080:6274` 时，浏览器的 origin 变成 `http://localhost:8080`，不再
  匹配容器内的端口，连接会 `403`。要么运行 `-e
  CLIENT_PORT=8080 -p 8080:8080`，要么设置 `-e
  ALLOWED_ORIGINS=http://localhost:8080,http://127.0.0.1:8080`。
</Callout>

## 在网络中托管

Inspector 默认绑定 `localhost`，其后端会生成进程，因此请把它暴露到网络中视为一个有意的决定。

Inspector 会拒绝绑定**通配符**全接口地址（`0.0.0.0`、`::` 以及每种等价写法），除非你设置 `DANGEROUSLY_BIND_ALL_INTERFACES=true`。绑定**特定**地址无需选择加入即可允许，因为那是一次刻意的暴露而非一次性地暴露所有接口——后者正是 DNS 重绑定攻击瞄准的形态。

| 目标                                         | 该怎么做      |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **让局域网中另一台机器能访问它** | `HOST=192.168.1.50`。默认的 origin 允许列表跟随绑定主机，因此 `http://192.168.1.50:6274` 无需更多配置即可被接受。            |
| **置于 TLS 或反向代理之后**            | 浏览器的 `Origin` 变成公共 origin，不会匹配绑定主机。设置 `ALLOWED_ORIGINS=https://inspector.example.com`。                |
| **通配符绑定（容器）**               | 设置 `DANGEROUSLY_BIND_ALL_INTERFACES=true`。loopback 访问开箱即用；以非 loopback 地址访问它需要 `ALLOWED_ORIGINS`。 |

<Callout type="warn">
`ALLOWED_ORIGINS` **替换**默认列表而不是合并。列出每一个你会浏览的 origin，包括你想保留的 loopback 形式：

```
ALLOWED_ORIGINS=http://localhost:6274,http://127.0.0.1:6274,http://192.168.1.50:6274
```

每个条目都必须包含协议；不带协议的值会被丢弃并给出警告。空值**不会**禁用检查；它会回退到默认值。没有任何旋钮可以关闭 origin 校验。

</Callout>

离开 loopback 时还有两个进一步的注意事项：

- **MCP Apps 的沙箱端口也必须可访问。** 它是一个独立的、默认动态的端口；用 `MCP_SANDBOX_PORT` 固定它并暴露或转发它。Docker 镜像只发布 `6274`。
- **MCP Apps 无法在 TLS 下或裸 IPv6 字面量下渲染。** 沙箱 URL 始终是明文 `http`，因此 `https://` 页面会作为混合内容拦截 iframe；而带括号的 IPv6 字面量不是有效的 CSP host-source，请用主机名或 IPv4 地址浏览。

无论何种形态：保持认证开启。不要在任何除你之外的人能访问的东西上设置 `DANGEROUSLY_OMIT_AUTH`。

## 开发工作流

一个在实践中很好用的循环：

<Steps>
  <Step>

### 从 CLI 开始

`--method initialize` 在一秒内确认服务端能启动、能握手，并报告
    你期望的能力，而且答案可机器读取。大多数“不工作”的情况
    最后都落在这里。


</Step>

<Step>

### 转入 web 客户端做探索

Schema 驱动的表单、渲染出的结果以及旁边的 Protocol 选项卡
    能让你快速找到工具表现异常的情形。


</Step>

<Step>

### 测试边缘情况

无效输入、缺失的必需提示词参数、并发调用，以及——
    对 HTTP 服务端——两个协议时代。验证_错误_和成功
    一样是有意为之的。


</Step>

<Step>

### 用 CLI 把它锁定下来

把发现变成一条 CI 断言：把 CLI 的 `--format json`
    输出管道给带 `--stored-auth-only` 的 `jq -e`，这样缺失令牌会快速失败
    而不是启动交互式 OAuth。完整的
    命令见[在 CI 中验证服务端](/docs/mcp/tools/inspector/cli#verify-a-server-in-ci)。


</Step>

</Steps>
