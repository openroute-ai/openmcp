title: 授权安全注意事项
---


<div id="enable-section-numbers" />

本文档概述了实现者在构建 MCP 客户端和服务端时**必须**考虑的安全要求。

此外，实现者**必须**遵循 [OAuth 2.1 第 7 节 "Security Considerations"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#name-security-considerations)中所述的 OAuth 2.1 安全最佳实践。

## 令牌受众绑定与校验

[RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) Resource Indicators 通过**在授权服务器支持该能力时**将令牌绑定到其预期受众，提供了关键的安全优势。为支持当前和未来的采用：

- MCP 客户端**必须**按[资源参数实现](/docs/mcp/specification/2026-07-28/basic/authorization#resource-parameter-implementation)一节的规定，在授权请求和令牌请求中包含 `resource` 参数
- MCP 服务端**必须**校验向其出示的令牌是专门为其使用而签发的

[安全最佳实践文档](/docs/mcp/tutorials/security/security_best_practices#token-passthrough)概述了为什么令牌受众校验至关重要，以及为什么明确禁止令牌透传。

## 令牌窃取

获取到客户端存储的令牌，或服务端缓存或记录的令牌的攻击者，可以通过对资源服务器而言看似合法的请求访问受保护资源。

客户端和服务端**必须**实施安全的令牌存储，并遵循 [OAuth 2.1 第 7.1 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.1)中所述的 OAuth 最佳实践。

授权服务器**应当**签发短期访问令牌，以降低令牌泄露的影响。对于公共客户端，授权服务器**必须**按 [OAuth 2.1 第 4.3.1 节 "Token Endpoint Extension"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.3.1)所述轮换刷新令牌。

## 通信安全

实现**必须**遵循 [OAuth 2.1 第 1.5 节 "Communication Security"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-1.5)。

具体而言：

1. 所有授权服务器端点**必须**通过 HTTPS 提供。
1. 所有重定向 URI **必须**为 `localhost` 或使用 HTTPS。

## 授权码保护

已经获得授权响应中所含授权码访问权限的攻击者，可以尝试用该授权码兑换访问令牌，或以其他方式利用该授权码。（进一步描述见 [OAuth 2.1 第 7.5 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5)）

为缓解此问题，MCP 客户端**必须**按 [OAuth 2.1 第 7.5.2 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5.2)实现 PKCE，并**必须**在继续授权之前验证 PKCE 支持。PKCE 通过要求客户端创建秘密的 verifier-challenge 对，确保只有原始请求方才能用授权码兑换令牌，从而帮助防止授权码拦截和注入攻击。

在技术上可行时，MCP 客户端**必须**按 [OAuth 2.1 第 4.1.1 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.1.1)的要求使用 `S256` 码质询方法。

由于 OAuth 2.1 和 PKCE 规范未定义客户端发现 PKCE 支持的机制，MCP 客户端**必须**依赖授权服务器元数据来验证这一能力：

- **OAuth 2.0 Authorization Server Metadata**：如果 `code_challenge_methods_supported` 缺失，则授权服务器不支持 PKCE，MCP 客户端**必须**拒绝继续。

- **OpenID Connect Discovery 1.0**：虽然 [OpenID Provider Metadata](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata) 未定义 `code_challenge_methods_supported`，但 OpenID 提供方通常会包含此字段。MCP 客户端**必须**验证提供方元数据响应中存在 `code_challenge_methods_supported`。如果该字段缺失，MCP 客户端**必须**拒绝继续。

提供 OpenID Connect Discovery 1.0 的授权服务器**必须**在其元数据中包含 `code_challenge_methods_supported`，以确保 MCP 兼容性。

## 混淆攻击（Mix-Up Attacks）

控制 MCP 客户端所交互的某个授权服务器的攻击者，可能会试图让客户端向其发送由另一个诚实授权服务器签发的授权码或令牌（一种混淆攻击，描述见 [RFC9207 第 1 节](https://datatracker.ietf.org/doc/html/rfc9207#section-1)）。[授权响应校验](/docs/mcp/specification/2026-07-28/basic/authorization#authorization-response-validation)规定了所需的缓解措施。

## 开放重定向

攻击者可能构造恶意重定向 URI，将用户引导至钓鱼网站。

MCP 客户端**必须**在授权服务器注册重定向 URI。

授权服务器**必须**对照预先注册的值校验精确重定向 URI，以防止重定向攻击。

MCP 客户端**应当**在授权码流程中使用并验证 state 参数，并丢弃任何不包含原始 state 或与之不匹配的结果。

授权服务器**必须**采取预防措施，防止将用户代理重定向到不受信任的 URI，应遵循 [OAuth 2.1 第 7.12.2 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.12.2)中给出的建议

授权服务器**应当**仅在其信任重定向 URI 时才自动重定向用户代理。如果该 URI 不受信任，授权服务器可以告知用户，并依赖用户作出正确决定。

## Client ID Metadata Document 安全

在实现 [Client ID Metadata Documents](/docs/mcp/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents) 时，授权服务器**必须**考虑 [OAuth Client ID Metadata Document 第 6 节](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-security-considerations)中详述的安全影响。关键考虑事项包括：

### 授权服务器滥用防护

获取元数据文档的授权服务器**应当**考虑[服务端请求伪造（SSRF）](https://developer.mozilla.org/docs/Web/Security/Attacks/SSRF)风险，如 [OAuth Client ID Metadata Document: Server Side Request Forgery (SSRF) Attacks](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-server-side-request-forgery)所述。

### Localhost 重定向 URI 风险

Client ID Metadata Documents 本身无法防止 `localhost` URL 冒充。

授权服务器：

- **应当**对仅使用 `localhost` 的重定向 URI 显示额外警告
- **可以**要求额外的证明机制以增强安全性
- **必须**在授权期间清晰显示重定向 URI 的主机名

### 信任策略

授权服务器**可以**实施基于域的信任策略来接受 Client ID Metadata Documents，如 Client ID Metadata Document 规范的[第 6.4 节](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-00.html#section-6.4)和[第 6.8 节](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-00.html#section-6.8)所述。

## 受骗代理问题（Confused Deputy Problem）

攻击者可以利用充当第三方 API 中介的 MCP 服务端，导致[受骗代理漏洞](/docs/mcp/tutorials/security/security_best_practices#confused-deputy-problem)。通过使用窃取的授权码，他们可以在未经用户同意的情况下获取访问令牌。

使用静态客户端 ID 的 MCP 代理服务端**必须**针对每个[动态注册的客户端](/docs/mcp/specification/2026-07-28/basic/authorization/client-registration#dynamic-client-registration)在转发到第三方授权服务器（可能要求额外同意）之前获得用户同意。

## 访问令牌权限限制

如果服务端接受为其他资源签发的令牌，攻击者就可能获得未授权访问或以其他方式攻陷 MCP 服务端。

MCP 服务端**必须**在处理请求之前校验访问令牌，确保该访问令牌是专门为 MCP 服务端签发的，并采取一切必要步骤确保不会向未授权方返回任何数据。

MCP 服务端**必须**遵循 [OAuth 2.1 - 第 5.2 节](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#section-5.2)中的指引来校验入站令牌。

MCP 服务端**必须**仅接受专门为其自身准备的令牌，并**必须**拒绝未在受众声明中包含自己的令牌，或以其他方式验证自己是该令牌的预期接收方。详情见[安全最佳实践令牌透传一节](/docs/mcp/tutorials/security/security_best_practices#token-passthrough)。

如果 MCP 服务端向上游 API 发起请求，它可能对上游 API 而言充当 OAuth 客户端。上游 API 所使用的访问令牌是由上游授权服务器签发的独立令牌。MCP 服务端**不得**透传其从 MCP 客户端收到的令牌。

MCP 客户端**必须**实现并使用 [RFC 8707 - Resource Indicators for OAuth 2.0](https://www.rfc-editor.org/rfc/rfc8707.html)中定义的 `resource` 参数，以明确指定请求令牌所针对的目标资源。此要求与 [RFC 9728 第 7.4 节](https://datatracker.ietf.org/doc/html/rfc9728#section-7.4)中的建议一致。这确保访问令牌绑定到其预期资源，且不能跨不同服务被滥用。
