<div id="enable-section-numbers" />

在 **stdio** 传输层中，客户端将 MCP 服务端作为子进程启动。两端通过子进程的标准流进行通信：

- 服务端从 `stdin` 读取 JSON-RPC 消息，并向 `stdout` 写入 JSON-RPC 消息。
- 每条消息都是单个 JSON-RPC 请求、通知或响应。
- 消息以换行符分隔，且**不得**包含嵌入的换行符。
- 服务端**可以**向 `stderr` 写入 UTF-8 字符串用于任何日志记录目的，包括信息性、调试和错误消息。
- 客户端**可以**捕获、转发或忽略服务端的 `stderr` 输出，且**不应当**假定 `stderr` 输出表示错误情况。
- 服务端**不得**向其 `stdout` 写入任何不是有效 MCP 消息的内容。
- 客户端**不得**向服务端的 `stdin` 写入任何不是有效 MCP 消息的内容。

标准流是规范的通道，但本绑定除进程生命周期外不依赖它们。线格式（在可靠双向字节流上每行一条换行符分隔的 JSON-RPC 消息）在 Unix 域套接字、TCP 连接或任何类似通道上均可原样工作。基于此类流构建的[自定义传输层](/docs/mcp/specification/2026-07-28/basic/transports#custom-transports)**应当**复用本页的分帧和消息规则；只有子进程特定的方面（启动、`stderr`、通过关闭流而关闭、进程重启）需要特定于通道的等价实现。

## 发送消息

客户端通过向服务端的 `stdin` 写入 JSON-RPC _请求_和_通知_来发送消息，每行一条。客户端**不得**写入 JSON-RPC _响应_。

## 接收消息

客户端从 `stdout` 读取服务端消息，每行一条。所有消息共享这一单一通道；不存在按请求的流。

服务端写入三类消息：

1. 对客户端请求的_响应_，通过 JSON-RPC `id` 关联。
2. 与进行中的请求相关的_通知_，如 `notifications/progress` 和 `notifications/message`。
3. 为活动的 [`subscriptions/listen`][subscriptions-listen] 请求投递的_通知_。客户端**必须**使用 `_meta` 中的 `io.modelcontextprotocol/subscriptionId` 字段关联它们；参见 [`SubscriptionsListenRequest`][subscriptions-listen-request]。

服务端**不得**向 `stdout` 写入 JSON-RPC _请求_。服务端到客户端的交互以 [`InputRequiredResult`][mrtr-input-required] 回复承载；参见[多轮往返请求][mrtr]。

## 请求元数据

stdio 传输层的所有请求元数据都内联在 JSON-RPC 消息体中。协议版本、每请求能力和可选的客户端身份位于 [`_meta.io.modelcontextprotocol/*`][meta-fields] 中；方法名和参数位于 JSON-RPC 规定的存储位置。这里没有头部层。

[meta-fields]: /specification/2026-07-28/basic/index#meta

## 取消

要取消一个进行中的请求，客户端**必须**发送一条引用该请求 ID 的 `notifications/cancelled` 通知。由于 stdio 是单一共享的双向通道，没有可关闭的按请求流。服务端**应当**在可行的情况下尽快停止已取消请求的工作，并**不得**再为其发送任何消息。完整规则参见[取消][cancellation]。

[cancellation]: /specification/2026-07-28/basic/patterns/cancellation

## 关闭

客户端**应当**通过以下方式发起关闭：

1. 关闭指向子进程（服务端）的输入流。
2. 等待服务端退出。
3. 如果服务端未在合理时间内退出，则使用适合操作系统的机制强制终止进程。

在 POSIX 系统上，强制终止通常从 [`SIGTERM`][sigterm] 升级到 `SIGKILL`。在 POSIX 信号不可用的 Windows 上，客户端可以使用 [`TerminateProcess`][terminateprocess] 或 [Job Objects][job-objects]。

服务端**应当**在其标准输入被关闭或读取返回文件结束（end-of-file）时立即退出。这是主要的优雅关闭信号，也是唯一可移植的信号，因此遵守它可减少强制终止的需要。

服务端**可以**通过关闭其面向客户端的输出流并退出来发起关闭。

## 意外终止

如果服务端进程意外退出，客户端**应当**重启它。由于协议是无状态的，任何进行中的请求都会直接丢失，客户端可以对全新的进程重试它们。活动的 [`subscriptions/listen`][subscriptions-listen] 流也必须在重启后重新建立。

## 向后兼容

同时支持现代（每请求元数据）MCP 版本和要求 `initialize` 握手的旧版版本的客户端，**应当**在发送任何其他请求之前用 [`server/discover`][server-discover] 进行探测，并在 `_meta` 中设置其首选的现代版本。探测有三种可能的结果：

- 服务端返回 `DiscoverResult`：服务端是现代版本。从 `supportedVersions` 中选择一个双方都支持的版本并继续。
- 服务端返回一个可识别的现代 JSON-RPC 错误，如 [`UnsupportedProtocolVersionError`][unsupported-version]：服务端是现代版本，但不支持所请求的版本。使用其通告的 `supported` 列表中的某个版本。**不**要回退到 `initialize`。
- 服务端返回任何其他错误，或在合理超时内未响应：服务端是旧版。回退到 `initialize` 握手。

回退**不得**绑定到某一特定错误码：旧版服务端以实现定义的错误（通常是 `-32601` 或 `-32602`）响应未知的 `initialize` 前请求，或完全不响应。

只支持现代版本的客户端无需探测，但探测仍然**建议**进行：一些旧版服务端不验证请求是否在 `initialize` 之后到达，会以旧版语义处理时代含义模糊的方法（如 `tools/call`）。改为探测可产生确定性的失败。

时代模型及面向实现者的兼容性矩阵参见[版本管理：向后兼容][lifecycle-compat]。
