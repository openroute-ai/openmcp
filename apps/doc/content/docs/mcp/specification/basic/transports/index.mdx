本页定义了传输层为了承载 MCP 消息所必须提供的功能、标准的传输层绑定，以及定义新的传输层的要求。

协议语义在每个传输层上都是相同的。传输层是一种**绑定**：它定义消息如何被分帧和投递、请求元数据如何被承载，以及取消和终止如何被发出信号。它不定义消息的含义：[消息模式](/docs/mcp/specification/2026-07-28/basic/patterns)是核心协议的一部分，且在每个绑定上都是相同的。绑定页面规定了标准的传输层：

1. [stdio](/docs/mcp/specification/2026-07-28/basic/transports/stdio)：通过客户端启动的子进程的标准流传递换行符分隔的消息。
2. [Streamable HTTP](/docs/mcp/specification/2026-07-28/basic/transports/streamable-http)：每条消息是对单一 MCP 端点的一次 HTTP POST；回复以 JSON 对象或请求作用域的 SSE 流的形式到达。

客户端和服务端也可以实现[自定义传输层](#custom-transports)。

## 消息

MCP 使用 JSON-RPC 对消息进行编码。JSON-RPC 消息**必须**为 UTF-8 编码。

绑定**必须**将客户端发送的_请求_和_通知_投递给服务端，并将服务端发送的_响应_和_通知_投递给客户端。不存在其他消息方向：按照[消息模式](/docs/mcp/specification/2026-07-28/basic/patterns)，服务端不发起 JSON-RPC 请求，客户端也不发送 JSON-RPC 响应。

## 请求元数据

所有协议元数据都在消息体中传输：每个请求都在 [`_meta.io.modelcontextprotocol/*`](/docs/mcp/specification/2026-07-28/basic/index#meta) 字段中携带其协议版本和客户端能力。

绑定**可以**额外将选定的消息体字段镜像到信封元数据中。Streamable HTTP 传输层将其镜像到 [HTTP 头](/docs/mcp/specification/2026-07-28/basic/transports/streamable-http#request-metadata)中，以便中间件可以在不解析消息体的情况下路由和检查请求。消息体始终是权威来源；镜像元数据的绑定需定义不匹配时如何被拒绝。

## 取消

每个绑定都定义了客户端如何放弃一个进行中的请求：在 stdio 上，客户端发送 `notifications/cancelled` 通知；在 Streamable HTTP 上，客户端关闭请求的响应流。协议层面的规则在所有地方都是相同的；参见[取消](/docs/mcp/specification/2026-07-28/basic/patterns/cancellation)。

## 自定义传输层

客户端和服务端**可以**实现额外的自定义传输机制以满足其特定需求。协议与传输层无关，可以在任何支持双向消息交换的通信通道上实现。

选择支持自定义传输层的实现者**必须**保留 JSON-RPC 消息格式、[消息模式](/docs/mcp/specification/2026-07-28/basic/patterns)和每请求元数据模型。自定义传输层**应当**记录其连接建立、消息分帧和取消模式，以促进互操作性。

在可靠双向字节流上运行的自定义传输层（如 Unix 域套接字或 TCP）**应当**复用 [stdio 分帧](/docs/mcp/specification/2026-07-28/basic/transports/stdio)，而不是定义新的分帧：stdio 绑定只是字节流上的换行符分隔的 JSON-RPC，只有其进程生命周期规则特定于标准流。

## 向后兼容

早期的协议修订版通过 `initialize` 握手建立了连接作用域的会话，并允许服务端发起 JSON-RPC 请求。与这些修订版互操作的客户端和服务端检测对端的时代，并按[版本管理：向后兼容](/docs/mcp/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions)中的描述回退，该部分包含面向实现者的兼容性矩阵。每个绑定页面都描述了其传输层特定的检测机制。
