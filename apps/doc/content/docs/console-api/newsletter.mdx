选型周刊的订阅与退订。两个端点都**不需要凭据**，因为它们服务的是公开落地页上的表单与邮件里的链接：要求先注册会把每个还没注册的访客挡在门外。

## `POST /api/newsletter/subscribe`

**鉴权**：无。`Content-Type: application/json`

**请求体**

| 字段     | 类型   | 必填 | 说明                                                              |
| -------- | ------ | ---- | ----------------------------------------------------------------- |
| `email`  | string | ✅   | 会被 trim 并转小写。最长 254 字符                                 |
| `source` | string |      | 来源标记。**白名单**：当前只接受 `landing-report`，其它值会被丢弃 |

`source` 是白名单而不是透传，因为它会被存下来、以后可能出现在邮件链接里——一个公开接口接受任意字符串，就是把别人的输入往下游存。

**响应**：`{ "ok": true }`

订阅是 **upsert**：重复提交同一个地址会重新订阅，而不是撞唯一索引失败。用 `onConflictDoUpdate` 是为了原子性，否则两个并发提交可能都先查不到、再一起插入。

**副作用**：立刻发一封确认邮件，邮件里带着报告对应的实时入口（飙升榜）。这样「已订阅」不是一句空话。

<Callout>
  邮件发送失败**不会**让请求失败，地址已经落库了。部署没配邮件服务时，地址同样会记下来，确认邮件的内容会打到服务端日志里。一个本地跑通的部署应该能在日志里看到完整流程。
</Callout>

**错误**

| 状态码 | `error`           | 条件                                          |
| ------ | ----------------- | --------------------------------------------- |
| `400`  | `invalid_request` | body 不是合法 JSON，或 `email` 不是字符串     |
| `400`  | `invalid_email`   | `email` 为空、超过 254 字符，或不符合邮箱格式 |

## `GET /api/newsletter/unsubscribe`

**鉴权**：URL 里的签名 token。

```html
<a href="/api/newsletter/unsubscribe?email=someone%40example.com&token=<hmac>">
  退订
</a>
```

`token` 是对规范化后的邮箱地址签的 HMAC（密钥 `BETTER_AUTH_SECRET`），所以这个接口可以公开，而不会变成「知道一个邮箱就能替别人退订」的漏洞。

**是 GET 而不是 POST**：收件人点开就该看到结果，不该要求先登录或再点一次确认。

**幂等**：地址不在库里、或者已经退订过，都算成功。收件人关心的是「我不再收到」，同一个链接重复点开不该报错。

**响应**：一个 HTML 页面（不是 JSON）。

| 状态码 | 页面                         |
| ------ | ---------------------------- |
| `200`  | 「已退订」/ "Unsubscribed"   |
| `400`  | 「链接无效」/ "Invalid link" |

<Callout>
  邮件里没有退订链接的情形：`BETTER_AUTH_SECRET` 未设置时无法签发
  token，此时确认邮件仍然会发，只是不带页脚链接。服务端会在日志里记一条
  warn。`BETTER_AUTH_SECRET` 是 better-auth
  自己的必需项，正常部署不会有这个情况。
</Callout>

## 与调度的关系

周刊邮件本身由调度器发送（见[调度器](./scheduler)），不在订阅时发送。这里的两个端点只负责**维护订阅名单**。
