`/api/v1/repos` 与 `/api/v1/projects` 是控制台仅有的两个机器对机器写入口。它们**用 API Key 鉴权**，Key 存在 `api_keys` 表里，逐 Key 带 scope：可以被单独吊销，也可以被单独授予某一项权限。

## 两个端点，两种权限

| 端点                     | Scope            | 写什么                                       | 公开站可见 |
| ------------------------ | ---------------- | -------------------------------------------- | ---------- |
| `POST /api/v1/repos`     | `repos:write`    | `repos`、`user_repos`                        | 否         |
| `POST /api/v1/projects` | `projects:write` | `projects`、README、技能文档                 | **是**     |

这条分界不是命名偏好。在 `projects` 上建一行就是**发布**：公开站的读取路径只认这张表。一把只该「登记仓库」的 Key 如果同时能调 `POST /api/v1/projects`，它就获得了把任意仓库推上公开站的权限。所以这两件事必须是两个 scope，由管理员逐 Key 决定谁拿哪一个。

<Callout type="warn">
  `projects:write` 默认**不在**任何自助签发的范围内。发布是运营动作，不是用户对自己数据的操作，所以它只能由管理员通过 `apiKeys.create` 显式授予。
</Callout>

## 鉴权

```
Authorization: Bearer <api-key>
```

**鉴权**：`Authorization: Bearer <api-key>`，Key 在 `api_keys` 表里按哈希查找。

响应带限流头（`X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`）。

| 状态码 | `error`    | 条件                                                     |
| ------ | ---------- | -------------------------------------------------------- |
| `401`  | `unauthorized` | 缺少、格式不对或无法识别的 Key                       |
| `403`  | `forbidden`    | Key 有效，但没有这个端点要的 scope                 |

Key 自带的 `submitter_id` 会被记成这次写入的归属，不需要也不接受调用方在 body 里自称是谁。

## `POST /api/v1/repos`

**登记一个仓库，让 radar 开始跟踪它。它不发布任何东西。**

接受两种请求体，**按形状区分**，不需要额外的判别字段。

### Body 形式一：`RepoInfo`

完整的仓库信息对象，与控制台自己调用 `fetchRepoInfo` 得到的形状一致。用于已经抓到数据的外部采集器——它推送过来，控制台就不必再调一次 GitHub API。

请求体是 `strict` 的：多一个未声明的字段就返回 `400`。这不是刁难，而是让「我以为推送了这个字段」变成一次响亮的失败而不是一次静默的丢失。

| 字段                       | 类型           | 必填 | 说明                       |
| -------------------------- | -------------- | ---- | -------------------------- |
| `name`                     | string         | ✅   | 仓库名                     |
| `fullName`                 | string         | ✅   | `owner/name`               |
| `owner`                    | string         | ✅   | owner 名                   |
| `ownerId`                  | number         | ✅   | owner 的数字 id，整数      |
| `createdAt`                | string         | ✅   | ISO 8601                   |
| `pushedAt`                 | string         | ✅   | ISO 8601                   |
| `lastCommit`               | string         | ✅   | ISO 8601                   |
| `description`              | string         |      | 默认 `""`                  |
| `homepage`                 | string         |      | 默认 `""`                  |
| `defaultBranch`            | string         |      | 默认 `""`                  |
| `stars`                    | number         |      | 默认 `0`，非负整数         |
| `topics`                   | string[]       |      | 默认 `[]`                  |
| `archived`                 | boolean        |      | 默认 `false`               |
| `commitCount`              | number         |      | 默认 `0`，非负整数         |
| `mentionableUsersCount`    | number         |      | 默认 `0`，非负整数         |
| `watchersCount`            | number         |      | 默认 `0`，非负整数         |
| `licenseSpdxId`            | string         |      | 默认 `""`                  |
| `pullRequestsCount`        | number         |      | 默认 `0`，非负整数         |
| `openIssuesCount`          | number         |      | 默认 `0`，非负整数         |
| `releasesCount`            | number         |      | 默认 `0`，非负整数         |
| `languages`                | string[]       |      | 默认 `[]`                  |
| `forks`                    | number         |      | 默认 `0`，非负整数         |
| `openGraphImageUrl`        | string         |      | 默认 `""`                  |
| `usesCustomOpenGraphImage` | boolean        |      | 默认 `false`               |
| `latestReleaseName`        | string         |      | 默认 `""`                  |
| `latestReleaseTagName`     | string         |      | 默认 `""`                  |
| `latestReleasePublishedAt` | string \| null |      | 从未发布过则 `null` 或省略 |
| `latestReleaseUrl`         | string         |      | 默认 `""`                  |
| `latestReleaseDescription` | string         |      | 默认 `""`                  |

<Callout type="warn">
  ISO 8601 字符串必须真的能被解析成日期。这里**不是**用的
  `z.coerce.date()`：它接受 `null`（解释为
  epoch）和数字字符串，两者都会把一个错误的日期悄悄存进去。
</Callout>

写入是 **upsert**：新仓库插入一行；已存在的仓库做**部分更新**，只覆盖本接口拥有的字段，README、README 翻译、图标与 OSS 图片 URL 这些由别的任务拥有的字段保持不动。

### Body 形式二：`{ url }`

调用方手上没有 GitHub 数据，只有一个仓库地址。控制台会去取。

| 字段  | 类型   | 必填 | 说明                   |
| ----- | ------ | ---- | ---------------------- |
| `url` | string | ✅   | GitHub 仓库地址        |

<Callout type="warn">
  这个端点**不接受** `type`。带着 `type` 的请求会返回 `400 type_not_accepted` 并指向 `POST /api/v1/projects`。
</Callout>

  在「登记」端点上接受一个类型字段，等于把「顺手就发布了」重新变成默认值——而那正是 `POST /api/internal/repos` 被拆掉的原因。想要项目，走另一个端点。

已存在的仓库不会重新抓取：控制台按 `owner/name` 查一次，命中就直接复用存下来的那行，省下一次 GraphQL 请求。

**响应**

```json
{
  "ok": true,
  "repo": {
    "id": "…",
    "full_name": "owner/repo",
    "stars": 12345
  },
  "created": true,
  "projectCount": 0
}
```

| 字段           | 含义                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| `created`      | `true` 表示这次插入了新行，`false` 表示刷新了已有行。`201` / `200` 同义 |
| `projectCount` | 已有多少 project 指向这个仓库。**这个端点自己不建 project**，所以非零只可能发生在仓库先前已被策展过时——它是用来区分「我登记了一个新仓库」和「我的 `type` 被静默忽略了」的 |

**错误**

| 状态码 | `error`    | 条件                                                    |
| ------ | ---------- | ------------------------------------------------------- |
| `400`  | `invalid_body` | body 不是合法 JSON，或既不符合 `RepoInfo` 也不符合 `{url}` |
| `400`  | `type_not_accepted` | body 带了 `type`                                   |
| `400`  | `invalid_url` | `url` 解析不出仓库                                    |
| `502`  | `create_failed` | 取仓库或落库失败                                    |
| `503`  | `github_unavailable` | 服务端缺 GitHub token。这是运维配置问题，不是请求问题 |

`400 invalid_body` 的 `detail` 指出**第一个出错的字段**——`RepoInfo` 更严格，所以报的是调用方真正搞错的那个字段，而不是一句误导性的 `url: required`。

## `POST /api/v1/projects`

**把一个仓库策展成一个 project，也就是发布它。**

幂等：按仓库去重。已经策展过的 URL 返回既有 project 与 `status: "existing"`，不会建第二行。

| 字段   | 类型   | 必填 | 说明                                                            |
| ------ | ------ | ---- | --------------------------------------------------------------- |
| `url`  | string | ✅   | GitHub 仓库地址                                                  |
| `type` | enum   |      | `application`、`skill`、`client`、`server`、`persona`。缺省 `application` |

<Callout>
  这个端点会**同步等待**：取仓库、翻译、同步技能、推送 webhook
  全在里面。声明的函数时长上限是 300
  秒，大仓库可能很久。调用方通常是在等一个用户，所以这次工作不能留给下一次定时扫描。
</Callout>

**响应**

```json
{
  "ok": true,
  "status": "created",
  "repo": { "full_name": "owner/repo" },
  "project": { "…": "Project 行" },
  "readme": { "…": "README 行" },
  "skills": { "count": 3, "translated": 2, "empty": false },
  "authorLinked": true,
  "delivered": true,
  "delivery": { "found": 3, "pushed": 3, "failed": 0 }
}
```

| 字段            | 含义                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `status`        | `created`（`201`）或 `existing`（`200`）                                                                                       |
| `delivered`     | **调用方唯一需要的标志**：全部已存技能都到达了 Web 服务，所以它要的技能在那里可以用了。`null` 表示没配下游，这不是本次调用的失败 |
| `skills`        | 本次同步到的技能数与翻译数                                                                                                     |
| `delivery`      | 投递明细。没配下游时整个键缺席                                                                                                 |

`type: "skill"` 且 `status: "existing"` 时，接口会**再跑一次**技能同步。这是唯一一次同步跑两遍：项目创建函数遇到已存在的项目会提前返回而不重跑，但一个「现在就要技能」的调用方如果拿到 `existing` 然后干等调度器，就白等了。重跑是幂等的。

`delivered` 只在 `type === "skill"` 时有值。其他类型没有技能文档可投递，所以不做这次投递，也不会给出一个关于零个技能的、调用方无从判断真假的 `true`。

**错误**

| 状态码 | `error`              | 条件                                                    |
| ------ | -------------------- | ------------------------------------------------------- |
| `400`  | `invalid_body`       | body 不是合法 JSON，或不符合 `{ url, type? }`          |
| `400`  | `invalid_url`        | `url` 解析不出仓库                                      |
| `502`  | `create_failed`      | 策展失败                                                |
| `503`  | `github_unavailable` | 服务端缺 GitHub token。这是运维配置问题，不是请求问题  |

**出站 webhook**：`type: "skill"` 时在同步完成后会把该项目所有技能推送到 `SKILLS_WEBHOOK_URL`，带 `Authorization: Bearer $SKILLS_WEBHOOK_TOKEN` 和用 `GITHUB_DATA_WEBHOOK_SECRET` 签名的请求体。被拒绝的投递会记在行上，由重试队列接手，而不是在这里丢掉。

## 已移除的端点

`POST /api/internal/repos` 已删除。它用全站共享的 `CONSOLE_API_TOKEN` 鉴权（无 scope、无归属、不可撤销），并在 URL 分支上调用 `createProjectFromRepo`——于是每个调用方都在替它发布。按形态改用上面的两个端点：带 `RepoInfo` 或只想登记的用 `/api/v1/repos`，要发布的用 `/api/v1/projects`。
