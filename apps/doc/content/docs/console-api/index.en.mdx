## What this is

The console is a service that continuously collects public repository data. It records the arrival time of every stargazer, and the judgements its rule set produces — the anomaly feed — plus the periodic rankings are the product surface. This section documents every endpoint that application serves: 17 routes across six kinds of caller.

| Caller               | Endpoints                               | Auth                                 | Page                                                      |
| -------------------- | --------------------------------------- | ------------------------------------ | --------------------------------------------------------- |
| Any key holder       | Repo profiles, range stats, rankings    | `Bearer <api-key>` (per-key scopes)  | "API reference" in the console's own docs                |
| External collectors  | Repository registration, publishing     | `Bearer <api-key>` (per-key scopes)   | [Writes](./projects)                                      |
| Schedulers           | Scheduled tasks, single-task trigger    | `Bearer CRON_SECRET`                 | [Scheduler](./scheduler)                                  |
| The web app          | Skill pull, newsletter                  | `Bearer SKILLS_WEBHOOK_TOKEN` / none | [Skill export](./skills-sync), [Newsletter](./newsletter) |
| Browsers             | Accounts, sessions, SMS and email codes | session cookie / one-time token      | [Authentication](./authentication), [Account](./account)  |
| The console frontend | 13 tRPC router groups                   | session + role                       | [tRPC](./trpc)                                            |

## Base URL

Every example below is relative to the console's own origin, https://vercelai.cn:

```bash
export CONSOLE_ORIGIN=https://vercelai.cn
curl "$CONSOLE_ORIGIN/api/v1/rankings/weekly" \
  -H "Authorization: Bearer $CONSOLE_API_KEY"
```

There is no CORS to handle with `curl`: these endpoints exist for machines, and they answer with `Content-Type: application/json`. Every one of them wants a credential — there is no anonymous bypass.

## Three shapes of authentication

There is no single authentication mechanism. There are four unrelated paths, and which one applies depends on who is calling.

### Scoped API keys

This is the path `/api/v1/*` takes. `Authorization: Bearer <api-key>`, where the key lives in the `api_keys` table and is **looked up by hash** rather than compared against an environment variable. What it buys over a shared secret is three things a shared secret structurally cannot do:

- **Revoked on its own.** Delete the row and that integration stops working, without rotating a site-wide variable and restarting.
- **Scoped.** `repos:write` and `projects:write` are different keys. `projects:write` means "put any repository on the public site", so it is deliberately in no self-service grant: only an admin can hand it out, explicitly, through `apiKeys.create`.
- **Attributed.** The key's own `submitter_id` is recorded as who submitted the write. The caller never has to name itself in the body, and is not believed if it does.

Rate limits are configured per key (`rpm` / `rpd`) because they protect the downstream: reading a ranking is cheap, while `POST /api/v1/repos` triggers a GitHub fetch. Their safe ceilings differ by an order of magnitude.

### Shared secrets

`Authorization: Bearer <secret>`, compared in constant time. The scheduler and the skill export use this. Each has its own secret:

| Variable                     | Guards                                                  | When unset        |
| ---------------------------- | ------------------------------------------------------- | ----------------- |
| `CRON_SECRET`                | `GET/POST /api/cron/github`, `POST /api/webhook/{task}` | Returns **404**   |
| `SKILLS_WEBHOOK_TOKEN`       | `GET /api/skills-sync/export`                           | Returns **404**   |
| `GITHUB_DATA_WEBHOOK_SECRET` | Signing outbound skill webhooks                         | Nothing is pushed |

<Callout>
  An unset secret produces `404`, not `401`. This is deliberate: an unconfigured
  instance should not confirm to anyone that a guarded write endpoint exists
  there, and confirming that is itself collectable information. **Do not** read
  this 404 as a wrong path and retry — it means the server is missing
  configuration.
</Callout>

These secrets do not expire, carry no scopes, and cannot be revoked individually: rotation means changing the environment variable and restarting. Both of these endpoints are fixed machine-to-machine internal integrations — the scheduler and the skill export — and the holder of the secret is by definition a trusted internal system. A per-key scope layer there would complicate operations without adding a boundary; a write endpoint that genuinely needs per-caller permissions takes the scoped API key above instead.

### Session cookies

`/api/auth/*`, `/api/user/*` and `/api/trpc/*` are guarded by the session cookie issued by [Better Auth](https://www.better-auth.com). In a browser this is an `HttpOnly` cookie; scripted callers use `credentials: "include"` and must add their origin to `BETTER_AUTH_TRUSTED_ORIGINS` for cross-origin requests.

### One-time tokens

The SMS paths use neither a session nor a shared secret:

- The slider challenge yields a token in the `X-Temp-Captcha-Token` request header. It is **single-use** and consumed on the request that presents it.
- The unsubscribe link carries an HMAC over the email address. Opening it twice is idempotent.

## Error format

The error shape depends on the auth layer. `/api/v1/*` returns `{"error": {"code", "message", "detail"?}}`; everything else returns `{"error": "<machine_code>"}`. The stable machine code in either shape (`error.code` / `error` itself) is the **only** thing to branch on — `message` and `detail` are human-facing copy and can change at any time. **Branch on the code, never on the text.**

## Versioning and compatibility

There is no version prefix. Every machine-to-machine read lives under `/api/v1/*`, and there is no anonymous JSON endpoint outside it.

Exactly one stability promise exists: **fields are added, never removed or repurposed.** A new field is not a breaking change, so callers must ignore fields they do not recognise. The scheduler and skill-export response shapes carry **no** such promise — they serve specific integrations that change together.

## Machine-readable entry points

The console publishes two text files for agents, generated from the same data as this section:

- <code>https://vercelai.cn/llms.txt</code> — an index of every page, with one
  quotable sentence each
- <code>https://vercelai.cn/llms-full.txt</code> — the full judgement rules, the
  FAQ verbatim, and the complete public-API field tables

Every number in those rules is interpolated from the console's own `THRESHOLDS`, so they cannot drift from production behaviour: change the bound, both change.
