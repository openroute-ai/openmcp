这四个端点**不需要鉴权**，也**不能写入**。它们是控制台唯一的匿名面：一个没有鉴权的端点绝不能有能力改数据。四个端点里的每一个都与一个 HTML 页面同源——页面与 JSON 读的是同一个函数、同一组默认参数，因此两者对「哪些行是公开的」不可能有分歧。

站内同源文档：`https://vercelai.cn/docs`。给 agent 读的同一份字段表在 `https://vercelai.cn/llms-full.txt`。

<Callout>
  这四个端点**没有速率限制**，也没有稳定性承诺之外的任何服务等级。要取全量数据请直接查数据库，不要靠翻页。
</Callout>

## `GET /api/rankings/week.json`

ISO 周内星标绝对增量前 100，同时给出相对增速排序。缺省为最近一个完整周。

**请求参数**

| 参数   | 类型   | 说明                                       |
| ------ | ------ | ------------------------------------------ |
| `year` | number | ISO 周的年份，四位数字。缺省为本周所在年。 |
| `week` | number | ISO 周序号，1–53。缺省为最近一个完整周。   |

**响应**

```json
{
  "period": "week",
  "year": 2026,
  "week": 38,
  "trending": [/* RankedProject[] */],
  "byRelativeGrowth": [/* RankedProject[] */]
}
```

`trending` 与 `byRelativeGrowth` 是**同一批项目**的两种排序：前者按绝对增量 `delta` 降序，后者按相对增速 `relativeGrowth` 降序，两边都是最多 100 条。**没有 `limit` 参数**：100 是计算本身的性质而不是请求的性质，一个只能把它调大的参数会让调用方把响应撑开。

**榜单条目**

| 字段                          | 类型           | 含义                                                                     |
| ----------------------------- | -------------- | ------------------------------------------------------------------------ |
| `fullName`                    | string         | `owner/name`，榜单的自然键                                               |
| `name`                        | string         | 仓库名，不含 owner                                                       |
| `description`                 | string         | 项目描述                                                                 |
| `stars`                       | number         | 周期结束时点的累计星标                                                   |
| `delta`                       | number         | 该周期获得的星标数，可为负                                               |
| `relativeGrowth`              | number \| null | 增量 ÷ 期初星标。期初为 0 时是 `null`，不是 `Infinity`                   |
| `tags`                        | string[]       | 从仓库 topics 归一化来的分类 code                                        |
| `ownerId`                     | number         | GitHub owner 的数字 id                                                   |
| `createdAt`                   | string         | 仓库创建时间，ISO 8601                                                   |
| `logo` / `iconUrl` / `avatar` | string \| null | 渲染列表用的标记，按这个优先级取；三个都是 `null` 是正常的，回退到首字母 |
| `anomaly`                     | object \| null | 该仓库当期最严重的一条未处理异动，带 `kind` / `severity` / `title`       |

**错误**

| 状态码 | 条件                                            |
| ------ | ----------------------------------------------- |
| `400`  | `week` 不是 1–53 的整数，或 `year` 不是四位数字 |
| `404`  | 该周没有记录。两个数组都是空的，不是空榜单      |

**缓存**：`Cache-Control: public, max-age=0, s-maxage=3600` —— CDN 缓存一小时，客户端不缓存。

## `GET /api/rankings/month.json`

字段与周榜完全一致，周期换成自然月。缺省为最近一个完整月。

**请求参数**：`year`（四位数字）、`month`（1–12）。

**响应**：`{ "period": "month", "year": …, "month": …, "trending": […], "byRelativeGrowth": […] }`

**错误**：`400` 当 `month` 不是 1–12；`404` 当该月没有记录。

<Callout>
  周榜与月榜的条数上限都是 100，而**站内页面只显示前 12**。页面每期只公布 12
  个是有意的：前 12
  是一条能读的结论，全量铺开是把判断责任推回给读者。两个数字不冲突，因为它们服务于两种读者。
</Callout>

## `GET /api/rankings/rising-stars.json`

某一自然年内星标绝对增量最大的项目，适合做年度回顾。判断「谁正在被新发现」请看周榜的 `relativeGrowth`，不要看这里——年度数据里所有人的基数都已经很大了。

**请求参数**：`year`（四位数字，缺省为上一个完整自然年，按应用时区口径）。

**响应**

```json
{
  "date": "2026-01-08T00:00:00.000Z",
  "count": 42,
  "projects": [
    {
      "name": "…",
      "slug": "…",
      "full_name": "owner/repo",
      "description": "…",
      "stars": 12000,
      "delta": 8400,
      "monthly": [120, 95, 0, null, 210, 180, 160, 150, 140, 130, 900, 6100],
      "tags": ["mcp", "agent"],
      "owner_id": 12345,
      "created_at": "2024-03-01T12:00:00.000Z",
      "icon": "https://…",
      "url": "https://…"
    }
  ],
  "tags": [{ "name": "…", "code": "…" }]
}
```

<Callout>
  这个产物的字段命名沿用发布物的形状：`full_name` 与 `created_at` 是
  snake_case，而两个周期榜是
  camelCase。这是刻意的——被文章引用的报告会按字段名被引用，改名等于让引用全部失效。
</Callout>

`monthly` 有 12 个元素，**12 月在前**，所以下标 0 是 12 月。没有记录的月份是 `null`，不是 `0`——这两者不同：`0` 表示「这个月有人测过，确实没有增长」。

**错误**：`400` 当 `year` 不是四位数字；`404` 当这一年没有入选项目。

## `GET /api/anomalies.json`

命中判定规则的仓库，按检测时间倒序。这是唯一面向 agent 的判定结果端点。

**请求参数**

| 参数      | 类型   | 说明                                                                                 |
| --------- | ------ | ------------------------------------------------------------------------------------ |
| `limit`   | number | 返回条数。默认与上限都是 100                                                         |
| `kind`    | enum   | `star_cliff`、`star_acceleration`、`release_stall`、`commit_stall`、`license_change` |
| `since`   | string | ISO 8601 时间戳，只返回该时刻之后检测到的                                            |
| `include` | `good` | 取 `good` 时把健康加速项也一并返回                                                   |

`kind` **必须**命中枚举。非法值返回 `400`，而不是被当成「除这些以外」——后者读起来像一个过滤器，实际行为是一次反转。

缺省只返回告警项：一个人问「有哪些异动」，想听的是出问题的那部分。要看健康加速项需要显式请求 `include=good`。

**响应**

```json
{
  "anomalies": [
    {
      "id": "…",
      "repo": "owner/repo",
      "owner": "owner",
      "name": "repo",
      "stars": 12345,
      "kind": "star_cliff",
      "severity": "down",
      "title": "最近三周新增 52 → 48 → 31",
      "magnitude": 21,
      "period": "2026-09-14T00:00:00.000Z",
      "detectedAt": "2026-09-19T02:14:00.000Z",
      "metric": { "…": "触发时的完整读数：基数、最新值、阈值" },
      "evidence": { "series": [{ "label": "…", "value": 0 }], "notes": ["…"] }
    }
  ],
  "count": 1,
  "generatedAt": "2026-09-19T02:14:05.000Z"
}
```

`severity` 取 `down` / `risk` / `notice` / `good`。`good` **只**给 `star_acceleration` 用：它存在是为了让这个站能证明自己没有过度报警，一个只会报忧的信号站无法证明这一点。

`magnitude` 是排序用的量级，含义随规则而变：断崖是丢失的星数，加速是超出阈值的部分，停滞是天数，许可证变更是 `0`。读的时候要按 `kind` 读。

`metric` 与 `evidence` 的存在是为了让调用方**不必回查判定代码**就能复核这次为什么算命中。

**错误**：`400` 当 `kind` 不在枚举里，或 `since` 不是可解析的 ISO 8601。

**为什么只有 `open` 的行**：被人工判为误报的记录留在库里，但不再出现在这里。这正是让误报率可统计的原因——这个流会在我们错的时候缩小，我们对的时候保持不变。

## 稳定性

这四个端点承诺字段**只增不改不删**。新增字段不构成破坏性变更，因此调用方应当忽略不认识的字段。除此之外没有其他承诺：没有鉴权、没有速率限制、没有 SDK、没有可用性保证。
