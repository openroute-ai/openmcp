四个端点，全部需要**会话**，全部只操作**当前登录账号自己**的资料。改密码会吊销其它会话；换手机号需要先验证码；头像上传只返回 URL，写入 `image` 仍由框架的 `/update-user` 完成。

## `POST /api/user/password`

**鉴权**：会话。`Content-Type: application/json`

设置或修改密码。走框架的服务端 API 而不是浏览器端，因为这里的两个账号需要不同的端点：`changePassword` 要拿当前密码比对，而**手机号注册的账号根本没有密码**，它需要的是 `setPassword`——那个端点是 server-only 的，浏览器里没有对应的调用。

**请求体**

| 字段              | 类型    | 必填 | 说明                                         |
| ----------------- | ------- | ---- | -------------------------------------------- |
| `newPassword`     | string  | ✅   | 8–128 个字符                                 |
| `hasPassword`     | boolean |      | 由设置页传入，**决定走哪个端点**，不要自己猜 |
| `currentPassword` | string  |      | `hasPassword: true` 时用于比对               |

<Callout>
  `hasPassword`
  由调用方传入而不在服务端重算：两个端点被反过来调用都是安全的（第二个会返回
  `PASSWORD_ALREADY_SET`），而让一个地方回答这个问题，比在这里写分支更值钱。
</Callout>

改密码时 `revokeOtherSessions` 是**打开**的：改密码正是有人认为密码泄漏时才会做的事。留着旧会话等于用与请求相反的方式回答那个担心。

**响应**：`{ "ok": true }`

**错误**

| 状态码 | `error`                                 | 条件                                            |
| ------ | --------------------------------------- | ----------------------------------------------- |
| `400`  | `invalid_request`                       | body 不是合法 JSON                              |
| `400`  | `password_too_short`                    | 长度不在 8–128                                  |
| `400`  | `wrong_password`                        | `currentPassword` 不对                          |
| `401`  | `unauthorized`                          | 没有会话                                        |
| `409`  | `password_already_set`                  | 账号已经有密码，却又调了 `setPassword`          |
| `500`  | `password_change_failed`（带 `detail`） | 其它失败。`detail` 只用于排查，不要匹配它的文本 |

## `POST /api/user/phone/code`

**鉴权**：会话。

发送绑定手机号的验证码。**三道守卫**（滑块、每号每分钟 1 次 / 每小时 5 次、每 IP 每小时 10 次）在这里同样成立，见[认证](./authentication)。

**请求头**：`X-Temp-Captcha-Token`（必需，一次性）

**请求体**：`{ "phoneNumber": "13800138000" }` —— 非数字字符会被剥掉，之后必须匹配中国大陆手机号 `^1[3-9]\d{9}$`。

**顺序是有意的**：先查这个号码是否已被别的账号占用，**再**花钱发短信。一个已经被占用的号码永远绑不上，发码是花钱买一个已经知道的答案。返回 `409` 不是泄漏——手机号登录流程本来就会回答同一个问题。

**响应**：`{ "ok": true }`

**错误**

| 状态码 | `error`                             | 条件                                                   |
| ------ | ----------------------------------- | ------------------------------------------------------ |
| `400`  | `invalid_request` / `invalid_phone` | body 非法，或号码格式不对                              |
| `400`  | `captcha_required`                  | 缺滑块 token，或它已被用过                             |
| `409`  | `phone_in_use`                      | 这个号码已属于别的账号                                 |
| `429`  | 限流原因原文                        | 触发了号码或 IP 的频率限制                             |
| `502`  | `send_failed`                       | 短信服务调用失败。**验证码已经写进库**，重试会发新的码 |
| `401`  | `unauthorized`                      | 没有会话                                               |

## `POST /api/user/phone/bind`

**鉴权**：会话。

把已验证的号码绑到当前账号。

**为什么直写数据库**：Better Auth 拒绝对应的 `/update-user` 写入——手机号插件挂在那个路径上并抛 `PHONE_NUMBER_CANNOT_BE_UPDATED`，理由是号码是在**登录时**认领的，不是事后认领的。这个端点就是那个「之后」。

**请求体**：`{ "phoneNumber": "13800138000", "code": "123456" }`

**响应**：`{ "ok": true, "phoneNumber": "13800138000" }`

**并发靠唯一索引仲裁**：上面那次查询和这次写入之间有窗口，两个并发请求可能都通过查询都到达写入，只有 `user.phone_number` 上的唯一索引能裁决。它的错误被翻译成 `phone_in_use`（`409`），而不是以 500 的形式漏出去。

验证码与登录验证码是分开的一套：`5` 次尝试上限，短期有效。

**错误**

| 状态码 | `error`             | 条件                             |
| ------ | ------------------- | -------------------------------- |
| `400`  | `invalid_request`   | body 非法，或号码/验证码格式不对 |
| `400`  | `invalid_code`      | 验证码不对或已过期               |
| `409`  | `phone_in_use`      | 号码已属于别的账号               |
| `429`  | `too_many_attempts` | 尝试次数超限                     |
| `401`  | `unauthorized`      | 没有会话                         |

## `POST /api/user/avatar`

**鉴权**：会话。`multipart/form-data`

上传头像，返回它的公开 URL。

**请求体**：字段名 `file`，类型必须是 `image/png`、`image/jpeg`、`image/webp` 或 `image/gif`，最大 **2 MB**。

**响应**：`{ "url": "https://…/avatar/1734….webp" }`

**只有 URL 离开这个端点。** 账号的 `name`、`image` 都通过框架的 `/update-user` 写：客户端拿到 URL 后自己写 `image`。如果上传成功而那次写入失败，最坏的结果是桶里多一个孤儿对象，而对象存储的版本策略本来就容得下它。

检查的是**声明的类型**而不是嗅探字节：头像会被 `<img>` 渲染，而类型决定浏览器会去解码什么。这个白名单之外的不会被存下来。

对象路径是 `mcp/authors/{userId}/avatar/{timestamp}.{ext}`。它**不用**仓库的路径生成器——那个按仓库名归档，头像属于账号，复用它等于凭空造一个仓库出来归档。

**错误**

| 状态码 | `error`                             | 条件                             |
| ------ | ----------------------------------- | -------------------------------- |
| `400`  | `invalid_request` / `file_required` | 不是 multipart，或缺 `file` 字段 |
| `401`  | `unauthorized`                      | 没有会话                         |
| `413`  | `too_large`                         | 超过 2 MB                        |
| `415`  | `unsupported_type`                  | MIME 类型不在白名单里            |
| `502`  | `upload_failed`                     | 对象存储调用失败                 |
| `503`  | `oss_not_configured`                | 部署没有配对象存储               |

<Callout>
  `hasPassword`、`phone.in_use`、`wrong_password` 这些都是**稳定的机器码**。请按
  `error` 分支，不要匹配文本。
</Callout>
